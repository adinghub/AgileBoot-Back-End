# 首页任务详情设计

## 1. 功能目标

当前首页待跟进任务已经具备：

1. 任务中心列表
2. 延后
3. 完成
4. 忽略
5. 恢复
6. 操作日志

但 App 前端如果要做任务详情页，仍然存在两个问题：

1. 需要先调任务列表接口拿基础信息
2. 再调日志接口拿时间线

同时前端还要自己判断：

1. 哪些按钮能点
2. 原始来源记录是否已经失效

因此本期补充首页任务详情接口。


## 2. 设计目标

### 2.1 一次返回详情页所需核心信息

详情接口一次性返回三类数据：

1. 任务基础信息
2. 可执行操作能力
3. 历史操作时间线
4. 推荐下一步动作

这样 App 详情页可以直接渲染，不需要额外拼装。

### 2.2 历史任务可看，但无效任务不可继续操作

有些任务记录虽然还在，但原始来源可能已经不存在，例如：

1. 用药提醒被删除
2. 体检报告被删除

这种情况下详情页仍应允许查看历史记录，
但不应再展示或启用无效操作按钮。


## 3. 接口设计

### 3.1 新增接口

新增接口：

`GET /app/follow-up/tasks/{taskId}`

### 3.2 返回结构

接口返回：

1. `taskInfo`：任务基础信息
2. `sourceAvailable`：来源记录是否仍可用
3. `canDelay`：是否允许延后
4. `canComplete`：是否允许完成
5. `canIgnore`：是否允许忽略
6. `canRestore`：是否允许恢复
7. `recommendedAction`：推荐下一步动作
8. `taskLogs`：操作时间线


## 4. 规则设计

### 4.1 按钮可操作规则

当前规则如下：

1. `canDelay`：来源记录存在时可操作
2. `canIgnore`：来源记录存在时可操作
3. `canRestore`：来源记录存在且当前任务状态不是“待跟进”时可操作
4. `canComplete`：仅报告建议任务，且来源记录存在时可操作

### 4.2 为什么不直接由前端自己推断

如果由前端自己推断，会产生两个问题：

1. 规则散落在客户端，后续改动容易不一致
2. 前端并不知道原始来源记录是否已经被删除

因此由后端统一输出按钮能力更稳妥。

### 4.3 与日志接口的关系

日志接口 `GET /app/follow-up/tasks/{taskId}/logs` 仍然保留。

原因是：

1. 某些页面只需要时间线，不需要完整详情
2. 保留独立日志接口后，前端后续也能按需复用


## 5. 实现说明

### 5.1 详情接口不新增数据表

本次只是对已有任务表和日志表做组合查询，
不需要新增数据库表结构。

### 5.2 历史可见原则

如果来源记录已经删除，详情接口仍返回：

1. 任务基础信息
2. 推荐下一步动作
3. 历史日志

只是把：

1. `sourceAvailable`
2. 各类 `canXxx`

设置为不可操作，提醒前端禁用按钮即可。
