# APP 端临时用药扣库存设计

## 1. 背景

当前个人药柜已经支持：

1. 新增个人药品
2. 引入系统药品到个人药柜
3. 手工补库存
4. 用药提醒完成后自动扣库存

但家里常备药还有一类真实场景没有覆盖：

1. 用户没有提前建立用药计划
2. 只是偶尔吃一次感冒药、咳嗽药、止痛药
3. 仍然希望库存被及时扣减
4. 后续还能知道是谁、什么时候、因为什么临时用了药

因此这里新增一条和“计划用药”并列的能力：

1. 不创建计划
2. 不创建提醒
3. 直接登记一次临时用药
4. 同步扣减库存
5. 保留临时用药记录与库存流水

## 2. 业务规则

### 2.1 默认批次规则

为了兼容家庭常备药“没有批号、没有效期”的场景，库存批次新增默认批次语义：

1. `batchNo` 可以为空
2. `expireDate` 可以为空
3. 当 `batchNo` 和 `expireDate` 都为空时，视为同一个默认批次
4. 默认批次在数据库中通过 `is_default_batch = 1` 显式标记
5. 同一用户、同一药品下，只允许存在一个默认批次库存桶

这样做的原因是：

1. 仅依赖空值语义，后续前端和排障时不容易一眼识别
2. 显式字段可以稳定支撑展示、扣减策略和后续统计

### 2.2 临时用药扣减规则

当用户发起一次临时用药时：

1. 必须是当前用户自己的个人药品，系统药品不能直接扣库存
2. 药品必须已启用库存跟踪
3. 扣减数量必须大于 0
4. 如果库存不足，本次临时用药直接失败，不允许只扣一部分

未指定具体批次时，后端扣减顺序固定为：

1. 先扣默认批次
2. 默认批次不足时，再按 FEFO（先到期先出）扣其它批次
3. 其它批次内部仍沿用现有排序：效期早优先，再按批号和批次 ID 稳定排序

这样做的原因是：

1. 家庭常备药最常见的就是“没有批号和效期的临时桶”
2. 用户录入过明确效期的批次，通常更希望这些批次保留给计划用药或精细管理

## 3. 数据结构改造

### 3.1 `drug_stock_batch`

新增字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `is_default_batch` | `SMALLINT` | 是否默认批次，`1` 表示“批号和效期都缺失时的默认库存桶” |

同时放宽：

1. `expire_date` 允许为空
2. 默认批次允许 `batch_no`、`expire_date` 同时为空

### 3.2 `drug_temporary_medication_record`

新增临时用药记录表，避免只靠库存流水备注反查业务语义。

核心字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `record_id` | `BIGINT` | 主键 |
| `owner_user_id` | `BIGINT` | 当前 App 用户 |
| `member_id` | `BIGINT` | 使用该药的家庭成员，可为空 |
| `drug_id` | `BIGINT` | 药品 ID |
| `used_quantity` | `NUMERIC(10,2)` | 本次使用数量 |
| `stock_unit_snapshot` | `VARCHAR(20)` | 扣减时的库存单位快照 |
| `use_time` | `TIMESTAMP` | 实际使用时间 |
| `symptom` | `VARCHAR(100)` | 用途 / 症状，如感冒、咳嗽、发热 |
| `remark` | `VARCHAR(255)` | 备注 |
| `deducted_quantity` | `NUMERIC(10,2)` | 实际扣减数量 |

### 3.3 `drug_stock_log`

新增字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `related_temp_medication_id` | `BIGINT` | 关联的临时用药记录 ID |

新增流水类型：

1. `TEMPORARY_USE_DEDUCT`

## 4. 后端接口

### 4.1 临时用药扣库存

- 方法：`POST`
- 路径：`/app/drugs/{drugId}/stock/temporary-use`

请求体：

```json
{
  "memberId": 1001,
  "usedQuantity": 2,
  "useTime": "2026-04-27 20:15:00",
  "symptom": "感冒",
  "remark": "晚饭后临时服用"
}
```

字段说明：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `memberId` | 否 | 使用该药的家庭成员 ID；为空表示这次不挂成员 |
| `usedQuantity` | 是 | 本次扣减数量，必须大于 0 |
| `useTime` | 否 | 实际使用时间；为空时后端默认取当前时间 |
| `symptom` | 否 | 用途 / 症状 |
| `remark` | 否 | 备注 |

返回体：

返回最新 `DrugDTO`，这样 App 可以直接刷新药品详情和库存卡片，不需要再额外拉一次详情。

```json
{
  "code": 0,
  "ok": true,
  "data": {
    "drugId": 321,
    "drugCode": "DRG321",
    "drugName": "布洛芬缓释胶囊",
    "stockQuantity": 8,
    "stockUnit": "粒",
    "stockTrackingEnabled": true,
    "stockBelowAlert": false,
    "stockBatches": [
      {
        "batchId": 11,
        "batchNo": null,
        "expireDate": null,
        "defaultBatch": true,
        "stockQuantity": 5
      },
      {
        "batchId": 15,
        "batchNo": "IBU-202603",
        "expireDate": "2027-03-31",
        "defaultBatch": false,
        "stockQuantity": 3
      }
    ]
  }
}
```

### 4.2 现有补库存接口兼容调整

接口仍为：

- `POST /app/drugs/{drugId}/stock/increase`

本次调整后：

1. `batchNo` 仍可为空
2. `expireDate` 改为可为空
3. 当 `batchNo` 和 `expireDate` 同时为空时，后端自动并入默认批次
4. 当只传一个值时，仍按普通批次处理

推荐 App 端文案：

1. 如果两者都不填，提示“将录入默认批次”
2. 如果录入了任一字段，就按普通批次库存处理

## 5. App 对接要求

### 5.1 药品详情 / 药品卡片新增入口

App 端在个人药品上新增 `临时用药` 入口。

入口原则：

1. 系统药品不显示该入口
2. 个人药品才允许执行
3. 执行成功后刷新药品列表和详情

### 5.2 临时用药表单

App 表单字段：

1. 家庭成员
2. 使用数量
3. 用药时间
4. 用途 / 症状
5. 备注

交互要求：

1. 页面标题：`临时用药`
2. 顶部展示当前药品与当前库存
3. 提交成功后 Toast：`临时用药已登记，库存已扣减`
4. 成功后返回最新药品详情

### 5.3 默认批次展示

App 展示批次库存时：

1. `defaultBatch = true` 显示为 `默认批次`
2. 默认批次没有效期时显示 `默认批次 · 无效期`
3. 普通批次继续沿用现有 `批号 + 效期 + 数量` 展示方式

## 6. 兼容性说明

### 6.1 为什么不把临时用药做成计划

原因很明确：

1. 用户只是偶尔吃一次
2. 没有未来重复提醒需求
3. 强制建计划会让操作路径过长
4. 业务语义上它是“库存事件 + 用药记录”，不是“待执行计划”

### 6.2 为什么要单独建记录表

如果只记库存流水，会有几个问题：

1. 无法稳定表达成员、症状、用药时间
2. 后续 App 若要做“最近临时用药记录”会很难查
3. 备注文本承载不了完整业务字段

所以这次明确把“库存变更”和“临时用药业务记录”拆成两层：

1. 记录表承载业务语义
2. 库存流水承载审计语义

## 7. 验收点

后端验收：

1. 无批号无效期时可补库存到默认批次
2. 临时用药可优先扣默认批次
3. 默认批次不足时会继续扣普通批次
4. 库存不足时临时用药失败
5. 会写入临时用药记录和库存流水

App 验收：

1. 药品页可发起临时用药
2. 可选择成员、数量、时间、症状、备注
3. 成功后药品库存立即刷新
4. 默认批次在界面上有明确展示，不再显示成“未填写批号 + 未填写效期”
