# 报告解析后台重试队列设计

## 1. 背景

当前报告上传后虽然已经走后台异步解析，但图片视觉结构化仍然会受外部大模型状态影响。

在联调中已经出现了比较典型的一类问题：

1. 请求参数已经改到可以正常发出；
2. 但多模态视觉调用在 15 秒超时附近失败；
3. 后端随即把本次解析当成“已完成但没有识别到指标”或者直接失败结束。

这会带来两个业务问题：

1. 用户上传后很快看到“没有结构化结果”，但实际上只是外部模型暂时慢了；
2. 即使几十秒后第三方服务恢复，当前报告也不会自动继续解析。


## 2. 目标

这次的目标不是把后台线程改成 `while(true)` 一直卡住等待成功，而是实现更稳的“任务队列 + 延迟重试”：

1. 上传后仍然立即返回，不阻塞用户；
2. 遇到外部模型超时、429、5xx 这类临时故障时，不立刻终止任务；
3. 解析成功前不写入新的结构化指标；
4. 成功后再统一落库；
5. 如果重试次数最终耗尽，再明确标记失败。


## 3. 为什么不用“线程里一直等到成功”

“一直等到成功”听起来简单，但工程上风险很高：

1. 一条任务可能长期占住工作线程；
2. 一旦外部网关长时间不可用，线程池会被慢慢拖空；
3. 没有退避的话，会不断打第三方接口，既浪费资源也更容易被限流。

因此本次采用“执行一次 -> 失败后延迟重新入队”的方式，替代死循环阻塞。


## 4. 方案设计

### 4.1 新增可重试异常类型

新增：

1. `HealthReportRetryableParseException`

它只表示“本次失败属于临时性问题”，例如：

1. 视觉模型请求超时；
2. 外部网关限流；
3. 5xx 服务端抖动；
4. 网络瞬时异常。

它不表示：

1. 文件本身损坏；
2. 请求参数确定错误；
3. 业务逻辑校验失败。


### 4.2 外部模型客户端识别可重试故障

改动位置：

1. `HealthReportExternalLlmClient`

新增两类“可重试结构化调用”入口：

1. `generateRetryableJsonText(...)`
2. `generateRetryableJsonTextWithImage(...)`

只有报告结构化主链路会使用它们。

识别规则：

1. HTTP `408 / 429 / 5xx` 视为可重试；
2. `Read timed out / timeout / Connection reset / Connection refused` 这类网络异常视为可重试；
3. 4xx 中更像参数错误的状态不自动重试，避免死循环。


### 4.3 后台解析任务改成“失败后重新入队”

改动位置：

1. `HealthReportApplicationService`
2. `ThreadPoolManager`

核心流程：

1. 首次上传后，任务进入后台队列执行；
2. 如果解析成功，立即正常落库；
3. 如果抛出 `HealthReportRetryableParseException`，不标记永久失败；
4. 系统计算下一次重试时间；
5. 任务以延迟方式重新加入后台队列；
6. 重试成功后再统一写入结构化结果。


### 4.4 状态对外表达

为了避免前端和运营人员误解，这次区分了三种状态语义：

1. `PROCESSING`
   当前仍在排队或重试中，不视为终态
2. `COMPLETED`
   已成功完成解析并产出最终结果
3. `FAILED`
   自动重试已耗尽，当前任务明确终止

在重试期间，还会把摘要文案更新成：

1. 已进入后台重试队列；
2. 预计多少秒后再次执行；
3. 成功后再写入结构化结果。


### 4.5 重试策略

新增配置：

1. `health.report.parser.async-retry-enabled`
2. `health.report.parser.max-async-retry-count`
3. `health.report.parser.async-retry-initial-delay-ms`
4. `health.report.parser.async-retry-max-delay-ms`

策略说明：

1. 默认启用自动重试；
2. 默认最多额外重试 1 次；
3. 默认首次延迟 30 秒；
4. 后续按指数退避；
5. 最大等待时间受上限控制。

特别约定：

1. `max-async-retry-count > 0` 表示有限重试；
2. `max-async-retry-count <= 0` 表示不限次数，持续留在后台队列中等待成功。


## 5. 预期收益

完成后，用户会感知到更合理的行为：

1. 外部模型偶发超时，不再立刻被当成“解析不到指标”；
2. 报告会在后台继续等待并自动重试；
3. 真正成功后才写入新的结构化结果；
4. 如果一直失败，也会在重试耗尽后明确给出失败状态。


## 6. 当前边界

这次实现的是“应用内延迟重试队列”，不是数据库持久化消息队列。

这意味着：

1. 应用进程运行期间，自动重试可以正常工作；
2. 如果服务在等待重试期间重启，内存中的这条延迟任务不会自动恢复；
3. 若未来要做到“重启后也继续重试”，再补数据库级任务表会更合适。

当前先做这一步，是因为它改动更小、收益已经很直接，也更适合当前联调阶段快速验证。
