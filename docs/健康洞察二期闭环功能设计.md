# 健康洞察二期闭环功能设计

## 1. 本期范围

本期在“健康洞察九功能工作台 1.0”基础上继续补三项更容易形成闭环的能力：

1. 健康问题中心
2. 就医资料包导出数据
3. 慢病专项模板

目标不是继续铺新入口，而是把已经产生的数据整理成用户可以持续跟踪、就诊时可以直接使用、创建慢病专项时可以快速套用的能力。

## 2. 健康问题中心

### 2.1 复用现有模型

项目已有：

- `health_problem`
- `health_problem_evidence`

本期不新增健康问题表，直接复用这两张表。

原因：

- 报告解析已经会把异常线索沉淀为健康问题
- 证据表已经能挂报告、指标等来源
- 继续使用同一问题表，后续慢病、复查、AI 解读都能围绕同一对象扩展

### 2.2 新增接口

接口：

- `GET /app/health-insights/health-problems?memberId=`

返回内容：

- 问题总数
- 跟进中数量
- 已缓解数量
- 已关闭数量
- 高风险数量
- 问题列表
- 每个问题最近证据

### 2.3 权限边界

如果传 `memberId`，后端先校验当前账号是否可访问该成员。

如果不传 `memberId`，后端只聚合当前账号可访问成员的问题。

## 3. 就医资料包导出数据

### 3.1 设计边界

本期返回结构化导出数据，不直接生成 PDF 文件流。

原因：

- App 当前已经支持预览、复制和系统文本分享，后续可继续扩展本地图片或 PDF 渲染
- 后端统一控制资料包字段口径
- 后续需要会员门禁时，可以在这个接口统一加门禁

### 3.2 新增接口

接口：

- `GET /app/health-insights/medical-visit-package/export-data?memberId=`

返回内容：

- 成员基础信息
- 过敏史、慢病史
- 慢病专项档案
- 近期报告
- 异常指标
- 当前用药计划
- 健康问题
- 就诊前检查清单

### 3.3 默认成员规则

如果不传 `memberId`，默认取当前账号可访问成员中的第一个成员生成资料包。

后续如果 App 做完整导出页，建议让用户先选择成员，再调用该接口。当前健康洞察弹层会基于该接口返回的结构化数据组装可复制、可系统分享的文本资料包。

## 4. 慢病专项模板

### 4.1 复用慢病病种配置

模板来源：

- `health_chronic_disease_type`

本期不新增模板表。

原因：

- 当前病种配置已经包含病种编码、名称、分类、关注指标、管理目标、随访建议
- 模板本质上是病种配置的 App 化展示
- 新增慢病时只维护配置，不需要 App 写死枚举

### 4.2 新增接口

接口：

- `GET /app/health-insights/chronic-disease-templates`

返回内容：

- 模板编码
- 模板名称
- 病种编码
- 病种名称
- 分类
- 默认管理目标
- 默认随访建议
- 重点指标关键词
- 推荐日记类型
- 建档提示

### 4.3 所有慢病支持原则

慢病专项仍坚持通用模型：

- `diseaseCode` 表达病种
- `focusIndicatorCodesJson` 表达标准指标
- `focusIndicatorKeywordsJson` 表达兜底关键词
- `defaultDiaryTypes` 由配置内容推导，不作为固定病种分支

这样可以支持高血压、糖尿病、高尿酸、哮喘、冠心病、肾病等所有慢病继续扩展。

## 5. App 交互

健康洞察页顶部新增三个轻量动作：

- 健康问题中心
- 资料包导出
- 慢病模板

三项能力当前都以底部弹层展示，原因是：

- 不破坏健康洞察工作台主页面结构
- 快速验证用户是否需要这些功能
- 后续使用频率上来后，可以再拆成独立页面

## 6. 动作闭环补充

### 6.1 健康问题状态流转

接口：

- `PUT /app/health-insights/health-problems/{problemId}/status`

请求体：

```json
{
  "problemStatus": 2,
  "remark": "本次复查指标恢复，先标记为已缓解"
}
```

状态值沿用 `health_problem.problem_status` 的既有口径：

- `1`：跟进中
- `2`：已缓解
- `3`：已关闭

权限规则：

- 后端先按 `problemId` 查询问题记录。
- 再使用问题所属 `memberId` 调用家庭成员编辑权限校验。
- 只有具备编辑权限的账号才允许修改状态，只读协同账号不能关闭或缓解问题。

实现边界：

- 本接口只更新状态、最后跟进时间和可选备注，不在本期自动删除证据。
- 返回值复用健康问题中心里的问题卡片 DTO，App 可以直接替换本地列表项，避免修改后重新拉完整中心数据。

### 6.2 慢病模板一键建档

接口：

- `POST /app/health-insights/chronic-disease-templates/create-profile`

请求体复用慢病专项建档命令：

```json
{
  "memberId": 1,
  "diseaseCode": "HYPERTENSION",
  "riskLevel": "MEDIUM",
  "currentSummary": "近期血压波动，需要持续记录",
  "remark": "从健康洞察模板创建"
}
```

实现规则：

- 健康洞察层只提供模板入口，不重新实现慢病建档业务。
- 后端委托 `ChronicDiseaseApplicationService#createProfile(...)`，因此病种配置校验、重复专项校验、默认管理目标填充仍然保持一套逻辑。
- App 侧从模板弹层进入建档表单，提交后不需要理解病种配置细节，只传 `diseaseCode`、成员、风险等级和当前情况摘要。

### 6.3 健康问题状态审计与时间线

新增表：

- `health_problem_status_log`

记录内容：

- `problemId`：对应健康问题
- `memberId`：问题所属家庭成员
- `operatorUserId`：执行状态变更的账号
- `beforeStatus` / `afterStatus`：变更前后状态
- `actionRemark`：可选操作备注
- `actionTime`：操作发生时间

新增接口：

- `GET /app/health-insights/health-problems/{problemId}/status-logs`

设计规则：

- 更新状态时由后端自动写审计，App 不能直接创建审计记录。
- 查询状态历史只要求当前账号可访问成员；更新状态仍要求成员编辑权限。
- 健康洞察时间线会把最近状态变更聚合成 `HEALTH_PROBLEM_STATUS` 事件，便于用户从工作台回看问题处理过程。
- App 问题卡增加“状态历史”入口，按时间倒序展示状态从哪一个值变成哪一个值，以及备注、操作时间和操作者昵称。
- 后端在查询状态历史时根据 `operatorUserId` 批量加载 `app_user.nickname`，DTO 返回 `operatorNickname`，避免 App 为每条审计记录额外请求用户信息。

### 6.4 健康问题和慢病专项双向关联

新增表：

- `health_problem_chronic_profile_link`

设计原因：

- 一个健康问题可能同时归属多个慢病专项，例如“肾功能异常”可能同时影响高血压、糖尿病和肾病管理。
- 一个慢病专项也可能关联多个健康问题，例如糖尿病专项可能同时关注血糖异常、尿微量白蛋白异常和体重异常。
- 因此本期使用多对多关联表，而不是在 `health_problem` 或 `health_chronic_disease_profile` 上追加单个外键。

关联字段：

- `problemId`：健康问题 ID。
- `profileId`：慢病专项 ID。
- `memberId`：两端共同所属家庭成员，用于权限和列表过滤。
- `ownerUserId`：数据归属账号，用于后续后台治理或迁移。
- `linkSource`：关联来源，当前 App 手动关联固定为 `MANUAL`，后续可扩展 AI 建议或规则推荐。
- `linkRemark`：用户或业务流程记录的关联备注。
- `linkTime`：最后一次确认关联的时间。

新增接口：

- `GET /app/health-insights/health-problems/{problemId}/chronic-profile-candidates`
- `POST /app/health-insights/health-problems/{problemId}/chronic-profiles`
- `DELETE /app/health-insights/health-problems/{problemId}/chronic-profiles/{profileId}`

请求体示例：

```json
{
  "profileId": 10,
  "linkRemark": "该异常需要纳入糖尿病专项跟进"
}
```

返回字段对齐：

- 健康问题中心的每个问题新增 `relatedChronicProfiles`，用于 App 在问题卡片展示已经关联的慢病专项。
- 慢病专项详情看板新增 `relatedProblems`，用于 App 在专项详情中展示该专项正在跟进的健康问题。
- 候选专项接口返回同一个 `HealthProblemChronicProfileDTO`，其中 `linked=true` 表示已关联，`linked=false` 表示可点击新增关联。

权限规则：

- 查询候选专项只要求当前账号可访问该健康问题所属家庭成员。
- 新增和解除关联要求当前账号具备该家庭成员编辑权限。
- 后端强制校验健康问题和慢病专项必须属于同一个 `memberId`，避免把 A 成员的问题关联到 B 成员的专项。

实现边界：

- 当前关联是用户确认后的显式关系，不由 App 根据病种名称或关键词自动推断。
- 重复关联时后端按幂等处理，更新备注和关联时间，不重复插入 active 记录。
- 解除关联只移除关联关系，不删除健康问题、证据或慢病专项档案。

## 7. 性能与索引

本期查询会频繁使用：

- `health_problem.member_id`
- `health_problem.problem_status`
- `health_problem.risk_level`
- `health_problem_evidence.problem_id`
- `health_problem_evidence.evidence_date`
- `health_chronic_disease_type.status`
- `health_chronic_disease_type.sort`
- `health_problem_status_log.problem_id`
- `health_problem_status_log.member_id`
- `health_problem_status_log.action_time`
- `health_problem_chronic_profile_link.problem_id`
- `health_problem_chronic_profile_link.profile_id`
- `health_problem_chronic_profile_link.member_id`

因此补充 PostgreSQL 增量索引，降低问题中心、模板列表、状态历史、健康时间线和问题-专项双向关联查询成本。
