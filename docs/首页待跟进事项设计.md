# 首页待跟进事项设计

## 1. 功能目标

首页看板已经能展示：

1. 今日提醒预览
2. 最近异常报告预览
3. 家庭成员卡片

但这仍然更像“信息展示”，还不是真正的“任务流”。

因此本期继续补充首页待跟进事项，目标是把当前用户最需要处理的事情集中收拢成一组首页待办。


## 2. 一期范围

### 2.1 当前实现

当前待跟进事项已经支持以下能力：

1. 聚合今日待处理用药提醒
2. 聚合最近异常报告建议
3. 接入首页运营任务
4. 支持任务延后处理
5. 支持手动完成任务
6. 支持忽略任务
7. 支持任务恢复
8. 支持任务已读状态
9. 支持个性化推荐排序
10. 支持独立任务中心与历史任务筛选

### 2.2 当前边界

当前阶段仍保留以下边界：

1. 首页仍只展示首屏预览，完整历史记录由任务中心承接
2. 提醒任务的真实执行闭环仍优先通过“已服药 / 已跳过”完成
3. 运营任务负责引导用户进入业务页，不在任务流里直接创建底层业务数据


## 3. 设计原则

### 3.1 任务优先，不按模块拆散

首页待跟进事项的目标不是重复展示提醒模块和报告模块的数据，而是从用户视角统一回答：

1. 现在最需要处理什么
2. 为什么需要处理
3. 下一步可以点哪里

### 3.2 任务来源实时聚合，状态与投放能力单独落表

当前实现仍然保持“原始业务数据实时聚合”的主思路，
但为了支撑读写状态、历史任务与运营投放，已经补齐三类独立数据承载：

1. `health_follow_up_task`：保存任务快照、已读状态、延后状态、完成状态、忽略状态
2. `health_follow_up_task_log`：保存任务已读、延后、忽略、恢复、完成等操作轨迹
3. `health_operation_task`：保存后台人工投放的首页运营任务

也就是说：

1. 任务来源仍然复用提醒、报告、运营投放等原始业务数据
2. 任务状态与操作轨迹单独落库，保证首页预览和任务中心口径一致

首页最终会把两层数据合并后再输出。

原始来源仍然直接复用：

1. 提醒数据
2. 报告异常建议数据
3. 运营任务数据

这样可以快速落地，也能保持口径和原业务模块一致。

### 3.3 任务优先级可解释

当前首页任务优先级规则非常明确：

1. 已经到点但还没处理的提醒
2. 今天稍后要处理的提醒
3. 最近异常报告的跟进任务
4. 当前命中有效时间窗口的运营任务

同时系统会返回 `sortReason`，用于解释这条任务为什么排在当前顺序。


## 4. 返回结构

## 5. 任务来源规则

### 5.1 提醒任务

首页会读取今日仍处于待处理状态的提醒：

1. 如果已经到点，则优先级最高
2. 如果是今天稍后时间点，则次高优先级

### 5.2 报告任务

首页会扫描最近异常报告，并继续复用报告异常建议摘要。

如果报告存在异常项，就生成一条“报告需要跟进”的首页任务。

这样首页可以直接引导用户进入报告详情继续处理。

### 5.3 运营任务

后台维护的首页运营任务只有同时满足以下条件时，才会进入首页任务流：

1. 任务状态为启用
2. 当前时间命中生效窗口
3. 归属当前 App 用户

运营任务进入首页后，继续复用统一任务导航协议，
因此 App 首页、任务中心和消息中心都能走同一套业务跳转语义。

### 5.4 统一动作规则

当前统一支持以下动作能力：

1. 已读
2. 延后
3. 完成
4. 忽略
5. 恢复

不同任务类型在当前节点具体允许执行哪些动作，
由详情接口里的 `canDelay`、`canComplete`、`canIgnore`、`canRestore` 实时返回，
前端无需自己硬编码判断。
