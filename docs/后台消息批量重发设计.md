# 后台消息批量重发设计

## 1. 功能目标

当前后台已经支持：

1. 消息审计列表
2. 消息审计详情
3. 单条人工重发

但当出现以下场景时，单条重发效率仍然不够：

1. 一批消息因为用户未注册设备而集中失败
2. 某个时间段内同类消息批量未送达
3. 运营需要对勾选出的多条失败消息统一补发

因此本期补充后台批量重发能力，支持后台勾选多条消息后一次执行补发，并返回逐条结果明细。


## 2. 设计原则

### 2.1 只按显式勾选的消息ID批量执行

当前批量重发不直接按筛选条件自动执行，
而是要求前端明确传入 `messageIds`。

这样可以避免：

1. 筛选条件过宽导致误补发
2. 后台误把不该发的历史消息一并重发
3. 无法准确回显每条被处理的消息

### 2.2 批量执行采用“部分成功”模型

批量重发时，若某一条消息失败：

1. 不会中断其他消息继续执行
2. 最终结果会返回成功数、失败数
3. 每条消息都有独立执行明细

这样后台可以一次性看清整批结果，而不是重复多次手动尝试。

### 2.3 单次批量上限控制为100条

为了避免单次请求过大、误触达范围过宽，
本期限制：

1. 单次最多重发 100 条

后续如果确实需要更大规模补发，再考虑引入异步任务化处理。


## 3. 接口设计

新增后台接口：

`POST /health/messages/batch-resend`

请求体示例：

```json
{
  "messageIds": [101, 102, 103]
}
```


## 4. 返回结构设计

批量结果同时返回两层信息：

### 4.1 顶部汇总

1. `requestCount`
2. `actualCount`
3. `successCount`
4. `failedCount`

### 4.2 每条执行明细

每条消息返回：

1. `messageId`
2. `success`
3. `channel`
4. `message`
5. `sendStatus`
6. `sendTime`
7. `sendRetryCount`


## 5. 业务规则

### 5.1 批量前先做去重

如果请求中同一个 `messageId` 重复出现，
系统只执行一次，避免重复补发。

### 5.2 单条失败不回滚整批

这是后台补救场景的关键规则：

1. 某条消息不存在
2. 某条消息数据不完整
3. 某条消息当前没有可用设备

都只会让该条失败，不会影响其他消息继续执行。

### 5.3 结果继续回写原消息记录

批量重发本质上还是逐条调用单条重发逻辑，
因此每条消息仍会继续回写：

1. 发送状态
2. 发送时间
3. 重试次数
4. 发送结果说明


## 6. 后续建议

建议下一步继续补：

1. 仅对失败消息开放批量重发按钮
2. 支持按筛选条件生成批量重发候选集
3. 大批量重发改为异步任务执行
4. 批量重发操作结果导出
