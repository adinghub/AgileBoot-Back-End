# 体检报告结果分析设计

## 1. 功能目标

体检报告上传一期完成后，报告已经能归档，但还缺少前端真正可消费的“结果层”。

因此本期继续补齐：

1. 报告指标结果录入
2. 指标异常自动判定
3. 报告分析摘要输出

这样 App 端就可以先落地一版可用的报告详情页：

1. 上半部分看报告基础信息
2. 中间看指标结果列表
3. 下半部分看异常提示摘要


## 2. 一期范围

### 2.1 已实现

当前阶段已支持：

1. 按报告维度维护多条指标结果
2. App 端整份覆盖保存指标列表
3. 后端按规则自动计算正常 / 偏低 / 偏高 / 异常 / 待判断
4. 输出报告分析摘要
5. 报告删除时同步删除指标结果

### 2.2 暂未实现

当前阶段暂未实现：

1. OCR 自动识别报告图片/PDF
2. 指标标准化映射
3. 医学规则引擎
4. AI 诊断建议
5. 后台人工审核结果流转


## 3. 数据模型

### 3.1 指标结果表 `health_report_item`

一份体检报告通常包含多条检查指标，所以单独建结果表。

核心字段如下：

1. `item_id`
2. `report_id`
3. `owner_user_id`
4. `item_code`
5. `item_name`
6. `result_value`
7. `result_unit`
8. `reference_min`
9. `reference_max`
10. `reference_text`
11. `abnormal_flag`
12. `sort`
13. `remark`

### 3.2 异常标记

异常标记采用统一枚举，方便前后端和后续规则模块复用：

1. `0`：待判断
2. `1`：正常
3. `2`：偏低
4. `3`：偏高
5. `4`：异常


## 4. 关键业务规则

### 4.1 指标结果必须挂在报告下

指标结果不是独立业务对象，而是报告的子集，因此所有保存与查询都必须基于 `report_id`。

同时还要校验：

1. 报告必须存在
2. 报告必须属于当前 App 用户

### 4.2 保存采用整份覆盖

当前一期不提供单条指标的零散增删改，而是前端每次提交整份报告当前的完整指标列表。

这样做的原因：

1. 用户通常一次录完一整张报告
2. 前端不需要维护复杂 diff
3. 后端可以在一次事务中统一重算摘要

### 4.3 异常判定优先走数值规则

当前自动判定规则分两层：

1. 如果结果值能解析成数字，且有参考上下限，就按数值比较
2. 如果数值规则不成立，再尝试通过“正常 / 阴性 / 阳性 / 异常 / ↑ / ↓”等常见关键字做轻量判断

若仍无法判断，则标记为 `待判断`。

### 4.4 报告主表保存摘要快照

虽然分析摘要可以实时计算，但主表仍保留一份 `analysis_summary` 快照。

这样后续：

1. 列表页可以直接展示
2. 首页健康看板可以直接读取
3. 后台也更容易做查询筛选


## 5. 接口设计

App 端新增三个接口：

1. `GET /app/reports/{reportId}/items`：查询报告指标列表
2. `PUT /app/reports/{reportId}/items`：覆盖保存报告指标
3. `GET /app/reports/{reportId}/analysis`：查询报告分析摘要


## 6. 与后续能力的衔接

这一版结构已经给后续扩展留了空间：

1. OCR 服务可以直接把解析结果写入 `health_report_item`
2. 医学规则引擎可以按 `abnormal_flag` 和指标名称继续扩展
3. 首页健康看板可以按成员聚合异常项
4. 后台后续可以增加报告结果审核页
