# 后台App设备活跃与推送审计设计

## 1. 设计目标

当前系统已经具备两块基础能力：

1. App 端会把设备注册到 `app_device`
2. 后端会把消息最近一次发送结果写到 `app_message`

但后台在排查“为什么用户没收到提醒”时，仍然缺少一个真正可操作的观察面：

1. 看不到当前到底有哪些设备仍然活跃
2. 看不到某个账号最近绑定了几台设备、最后活跃时间分别是什么
3. 看不到某次 Push 到底发给了哪些设备
4. 看不到哪台设备成功、哪台设备失败、失败原因分别是什么

因此本期设计目标是补齐后台管理视角，让后台可以直接回答：

1. 某个用户当前有哪些可推送设备
2. 这些设备最近是否活跃
3. 某条提醒/某条报告消息整体是否发送成功
4. 该次发送具体命中了哪些设备
5. 失败是不是因为没有设备、设备停用、还是厂商通道异常


## 2. 当前能力与限制

### 2.1 当前已经能看到什么

基于现有表结构，后台已经可以直接拿到：

1. `app_device`
   - 当前账号有哪些设备
   - 设备平台、型号、厂商、系统版本、App版本
   - 设备是否启用
   - 最后活跃时间
2. `app_message`
   - 某条消息最近一次发送状态
   - 最近一次发送时间
   - 最近一次发送通道
   - 最近一次发送结果说明
   - 失败原因统计

这意味着：

1. “账号级是否有活跃设备”已经可以做
2. “消息整体最近一次是否成功”已经可以做

### 2.2 当前还看不到什么

现有结构的核心缺口是：

1. `app_message` 只保存“整条消息最近一次发送结果”
2. `AppPushMedicationReminderNotifier` 当前是按设备列表批量派发，但没有把“设备级发送结果”单独落库

因此目前后台还无法准确回答：

1. 同一条消息命中了哪几台设备
2. 多设备用户里，究竟是哪一台成功、哪一台失败
3. 某次厂商批量响应里，失败是否集中在某个平台或某个设备

结论是：

1. 设备活跃管理可以直接基于现有表建设
2. 设备级 Push 成功率审计必须补一张新表


## 3. 设计原则

### 3.1 先复用现有数据，再补最小必要表

本期不推倒现有消息中心和设备表设计，只做两层扩展：

1. 复用 `app_device` 做设备活跃管理
2. 复用 `app_message` 做消息整体发送审计
3. 新增设备级推送审计表，补足“到底哪台设备成功/失败”这个缺口

### 3.2 后台页面按“设备管理”和“推送审计”分成两块

原因是这两个问题关注点不同：

1. 设备管理回答“当前是否有可推设备”
2. 推送审计回答“某次推送是否真正送达目标设备”

如果强行揉成一个页面，会导致筛选口径、展示维度和操作目标都混在一起，不利于排障。

### 3.3 活跃不等于在线

后台页面里必须明确区分：

1. `启用状态`
   - 来自设备表 `status`
2. `最近活跃`
   - 来自设备表 `last_active_time`
3. `最近推送是否成功`
   - 来自消息表/设备推送审计表

这样可以避免把“设备最近活跃过”误解成“现在一定能推成功”。


## 4. 后台模块拆分

### 4.1 模块一：App设备管理

建议后台新增菜单：

1. `健康管理 / App设备管理`

主要目标：

1. 查看账号下有哪些设备
2. 判断设备当前是否仍可用于 Push
3. 识别长期未活跃、已停用、平台分布异常等问题

### 4.2 模块二：Push推送审计

建议后台新增菜单：

1. `健康管理 / Push推送审计`

主要目标：

1. 查看某条消息的整体发送结果
2. 查看设备级发送明细
3. 排查失败是否由“无设备 / 设备停用 / 厂商异常”引起

### 4.3 与现有后台消息审计的关系

本期建议保留现有：

1. `后台消息审计`
2. `后台消息统计看板`

并形成三层结构：

1. 消息审计
   - 看“这条业务消息最近一次整体发送结果”
2. 设备管理
   - 看“这个账号当前有没有可推设备”
3. Push推送审计
   - 看“这条消息究竟打到了哪些设备、哪些失败”

#### 5.1.4 活跃状态口径

建议后台统一给出派生状态：

1. `ACTIVE`
   - 启用中，且 `last_active_time` 在最近 7 天内
2. `SILENT`

3. `STALE`
   - 启用中，最近 30 天无活跃
4. `DISABLED`
   - 设备已停用

这样页面不用直接把时间差交给运营或客服自己算。

1. 基础信息

其中“最近推送汇总”建议包含：

1. 最近一次发送时间
2. 最近一次发送状态
3. 最近一次失败原因
4. 近7天成功率
5. 命中的业务场景分布

#### 5.1.6 后台操作

一期建议支持：

1. 查看详情

3. 查看该设备最近推送明细

1. 发送测试 Push

## 6. 数据结构设计

### 6.1 继续复用现有表

继续使用：

1. `app_device`
2. `app_message`

用途分别是：

1. `app_device`
   - 当前设备资产管理
2. `app_message`
   - 当前消息整体发送状态审计

### 6.2 新增设备级推送审计表

建议新增：

`app_push_delivery_log`

建议字段如下：

1. `delivery_id`
2. `message_id`
3. `owner_user_id`
4. `member_id`
5. `business_scene`
6. `business_id`
7. `device_id`
8. `device_code`
9. `push_platform`
10. `device_status_snapshot`
11. `device_token_masked`
12. `send_channel`
13. `send_status`
14. `failure_reason_category`
15. `failure_reason_message`
16. `vendor_code`
17. `vendor_message`
18. `retry_no`
19. `send_time`
20. `create_time`
21. `deleted`

### 6.3 字段说明

关键说明如下：

1. `message_id`
   - 关联消息中心主表，便于从消息审计跳转到设备级明细
2. `device_id / device_code`
   - 记录当次命中的设备
3. `device_status_snapshot`
   - 保存发送当时设备状态快照，避免后续设备被停用后无法还原历史现场
4. `device_token_masked`
   - 仅保存脱敏值，例如前3后4，便于排障但不暴露完整 token
5. `failure_reason_category`
   - 用于统一失败原因分类，便于统计聚合
6. `vendor_code / vendor_message`
   - 预留真实厂商回执信息
7. `retry_no`
   - 一条消息对同一设备的第几次尝试

### 6.4 失败原因分类建议

建议统一维护失败原因分类：

1. `NO_ACTIVE_DEVICE`
2. `DEVICE_DISABLED`
3. `DEVICE_TOKEN_EMPTY`
4. `VENDOR_REJECTED`
5. `CHANNEL_EXCEPTION`
6. `UNKNOWN`

这样后台统计不会被“同义不同文案”打散。


## 7. 后端实现设计

### 7.1 设备管理查询

建议新增领域服务：

1. `AppDeviceAdminApplicationService`

主要职责：

1. 设备分页查询
2. 设备统计概览
3. 设备详情
4. 设备最近推送汇总计算

### 7.2 推送审计查询

建议新增领域服务：

1. `AppPushDeliveryApplicationService`

主要职责：

1. 设备级推送审计分页查询
2. 推送审计详情
3. 推送统计看板

### 7.3 发送链路改造

当前 `AppPushMedicationReminderNotifier` 与其他 Push 发送器，需要补一层“设备级发送结果落库”。

建议改造原则：

1. 查询出活跃设备后，先形成目标设备快照
2. 每次发送结束后，按设备写 `app_push_delivery_log`
3. 如果厂商只返回批量结果，没有逐设备回执，则按批量结果回填所有目标设备
4. 如果根本没有目标设备，则：
   - `app_message` 继续记录整体失败
   - 不写设备级日志
   - 失败原因统一记为 `NO_ACTIVE_DEVICE`

### 7.4 与现有消息审计的协同

现有 `HealthAppMessageController` 不需要下线，建议继续保留作为“消息整体视角”。

新增页面和接口后，后台排障路径可以是：

1. 先在消息审计看这条消息整体成功还是失败
2. 如果失败原因是 `NO_ACTIVE_DEVICE`
   - 直接跳设备管理页看当前账号设备
3. 如果整体发送成功但用户仍说没收到
   - 跳 Push 推送审计看设备级明细


## 8. 后台接口设计

### 8.1 设备管理接口

建议新增：

1. `GET /health/push/devices`
2. `GET /health/push/devices/statistics`
3. `GET /health/push/devices/{deviceId}`
4. `POST /health/push/devices/{deviceId}/disable`

### 8.2 推送审计接口

建议新增：

1. `GET /health/push/deliveries`
2. `GET /health/push/deliveries/statistics`
3. `GET /health/push/deliveries/{deliveryId}`

### 8.3 与现有后台消息接口联动

现有：

1. `GET /health/messages`
2. `GET /health/messages/statistics`
3. `GET /health/messages/{messageId}`

建议补充返回字段或跳转关系：

1. `targetDeviceCount`
2. `successDeviceCount`
3. `failedDeviceCount`
4. `lastFailureReasonCategory`

这样消息审计页不用完全跳出去，也能先看到设备级概况。

## 10. 一期与二期范围

### 10.1 一期建议落地范围

一期建议先做：

1. App设备管理页
2. 设备统计概览

这样就已经能解决 80% 的后台排障诉求。

### 10.2 二期建议扩展范围

二期可以继续补：

1. 测试 Push
2. 设备导出

5. 无设备 token 比例告警

## 11. 预期收益

完成后，后台可以直接获得三类能力：

1. 设备资产可见
   - 知道每个账号当前有没有可推送设备
2. 推送问题可定位
   - 知道失败是无设备、设备停用还是通道异常
3. 多设备行为可解释
   - 知道同一条消息具体是哪台设备成功、哪台设备失败

最终效果是把“用户说没收到提醒”从黑盒问题，变成后台可观察、可验证、可追踪的问题。
