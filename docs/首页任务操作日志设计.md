# 首页任务操作日志设计

## 1. 功能目标

首页待跟进任务已经支持：

1. 延后
2. 完成
3. 忽略
4. 恢复

但当前只有“最终状态”，还缺少完整的操作轨迹。

这会带来两个问题：

1. App 前端在任务详情页无法给用户展示时间线
2. 后续排查“为什么这个任务消失/恢复/延期”时缺少追溯依据

因此本期新增首页任务操作日志能力。


## 2. 设计原则

### 2.1 任务状态与任务日志分离

`health_follow_up_task` 继续负责保存“当前生效状态”，例如：

1. 当前是否已延后
2. 当前是否已忽略
3. 当前是否已完成

`health_follow_up_task_log` 专门保存“发生过哪些动作”，例如：

1. 09:10 用户把任务延后到今晚 20:00
2. 14:30 用户又把任务恢复显示
3. 18:00 用户再次忽略

这种拆分方式能够同时满足：

1. 首页查询高效
2. 时间线完整可追溯

### 2.2 日志只追加，不覆盖

日志表采用追加写入模式。

每次调用以下接口时，都新增一条日志：

1. `POST /app/follow-up/tasks/delay`
2. `POST /app/follow-up/tasks/complete`
3. `POST /app/follow-up/tasks/ignore`
4. `POST /app/follow-up/tasks/restore`

这样可以确保历史操作不会被后一次动作覆盖掉。


## 3. 数据模型

### 3.1 表 `health_follow_up_task_log`

核心字段如下：

1. `log_id`
2. `task_id`
3. `owner_user_id`
4. `member_id`
5. `task_type`
6. `source_id`
7. `action_type`
8. `before_status`
9. `after_status`
10. `action_remark`
11. `delayed_until_snapshot`

### 3.2 操作类型

当前定义四类操作：

1. `DELAY`
2. `COMPLETE`
3. `IGNORE`
4. `RESTORE`

### 3.3 状态快照

为了让前端直接展示“从什么状态变成什么状态”，
日志里同时记录：

1. `before_status`
2. `after_status`

例如：

1. 延后：`待跟进 -> 已延后`
2. 恢复：`已忽略 -> 待跟进`
3. 完成：`已延后 -> 已完成`


## 4. 接口设计

### 4.1 新增接口

新增接口：

`GET /app/follow-up/tasks/{taskId}/logs`

### 4.2 查询方式说明

这里选择按 `taskId` 查询，而不是按 `taskType + sourceId` 查询，主要考虑：

1. 任务中心列表天然已经返回 `taskId`
2. 对前端来说路径更直观
3. 后续如果任务记录附加更多扩展属性，接口仍然稳定

### 4.3 返回内容

日志接口返回每一条动作的：

1. 操作类型
2. 操作类型名称
3. 操作前状态
4. 操作后状态
5. 操作备注
6. 延后时间快照
7. 操作时间


## 5. 处理规则

### 5.1 日志写入时机

任务表保存成功后，立即追加一条日志。

这样可以确保：

1. 日志中的 `task_id` 一定有效
2. 日志状态与任务最终状态保持一致

### 5.2 事务一致性

任务状态更新和任务日志写入放在同一事务中执行。

如果任何一步失败，则整体回滚，避免出现：

1. 任务状态已改，但日志没写成功
2. 日志写成功，但任务状态没更新

### 5.3 日志排序

当前接口按“最近操作优先”返回：

1. `create_time` 倒序
2. `log_id` 倒序

这样前端任务详情页打开后，用户可以先看到最新一次动作。
