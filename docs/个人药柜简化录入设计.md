# 个人药柜简化录入设计

## 1. 背景

当前个人药柜能力已经支持较完整的药品档案录入，包括：

1. 药品名称
2. 规格
3. 厂家
4. 通用名
5. 剂型
6. 备注
7. 库存单位
8. 初始库存
9. 预警值

但从真实使用场景看，普通用户在录入家庭常备药时，往往并不会非常精确地输入：

1. 药品规格
2. 生产厂家
3. 通用名
4. 剂型

用户更常见的输入方式是：

1. 先输入一个自己认识的药品名称
2. 再选择一个最小使用单位
3. 如果愿意，再补录当前库存和预警值

因此当前阶段更适合把个人药柜录入体验收敛到“轻量录入”，先降低录入门槛，同时保留既有扩展能力，便于后续再逐步放开更完整的药品档案字段。


## 2. 本次设计目标

本次目标不是删除既有药品能力，而是做“当前阶段默认简化”：

1. 保留既有药品字段与扩展空间。
2. 当前产品主流程只要求用户录入最少必要信息。
3. 库存仍然按用户选择的单位维护。
4. 单位不允许用户自由输入，改为使用后台统一维护并下发的单位字典。
5. 药品名称在“当前用户自己的药柜范围内”保持唯一。
6. 如果用户需要区分同类药品，通过提示引导其在名称中补充规格或用途信息。


## 3. 核心设计

### 3.1 当前录入模式

当前阶段手工新增个人药品时，主流程只要求：

1. `drugName`：药品名称
2. `stockUnitCode` / `stockUnitName`：库存单位

可选填写：

1. `stockQuantity`：初始库存
2. `stockAlertThreshold`：库存预警值
3. `remark`：备注
4. `drugImageUrl`：药品图片

保留但默认不强调、不强制填写：

1. `genericName`
2. `specification`
3. `manufacturer`
4. `dosageForm`
5. `brandName`
6. `indication`
7. `usageInstruction`

产品层建议：

1. 新增药品弹窗默认只展示“药品名称、单位、初始库存、预警值”。
2. 其他字段放到“补充信息”折叠区。
3. 后续如需恢复完整录入，只需要打开前端表单与校验，不需要推翻当前数据结构。

### 3.2 库存单位改为系统维护

单位不再允许用户自由输入，而是由后台维护一套标准单位字典，前端负责搜索和选择。

建议单位范围优先覆盖常见最小使用单位，例如：

1. 片
2. 粒
3. 支
4. 袋
5. 盒
6. 瓶
7. ml
8. g

说明：

1. 当前库存按用户所选单位直接维护，不做换算。
2. 单位本质上是“当前库存维护单位”与“提醒扣减单位”的统一口径。
3. 为避免后续扣减混乱，产品上优先引导用户选择最小使用单位，而不是包装单位。

### 3.3 药品名称唯一策略

药品名称唯一范围定义为：

1. 同一 App 用户自己的药柜内唯一
2. 不做全平台唯一
3. 不与系统药品全局名称做唯一冲突

这里的唯一性建议仍然基于 `drugName` 本身，而不是“名称 + 规格 + 厂家”组合。

原因：

1. 当前产品主流程已经刻意简化，不能把唯一性建立在用户未必会填写的字段上。
2. 如果唯一性规则过于复杂，前端和后端判断口径容易不一致。
3. 名称唯一更符合当前阶段“快速录入”的产品目标。

### 3.4 重名提示策略

由于用户可能确实存在同类药品需要区分，例如不同规格、不同用途、不同家庭成员使用场景，因此需要在校验失败时给出明确引导。

建议提示文案：

1. `药品名称已存在，请在名称中补充规格或用途区分，例如：阿莫西林(0.25g)、阿莫西林-儿童备用`

这样做的原因是：

1. 当前唯一键仍然是名称本身。
2. 规格和备注虽然保留，但不参与当前唯一性判断。
3. 通过名称补充区分信息，可以在不增加录入复杂度的前提下解决重名问题。


## 4. 后端建议

### 4.1 数据层

当前建议：

1. 不删除既有扩展字段。
2. 不因为本次简化录入而裁剪药品主档能力。
3. 药品库存仍按当前选定单位维护。
4. 后续如果需要恢复规格、厂家、批号效期等能力，直接在既有结构上扩展即可。

也就是说，本次更偏向“产品录入模式调整”，而不是“数据库能力收缩”。

### 4.2 药品图片

建议支持药品图片，但明确为非强制字段。

当前阶段建议规则：

1. 每个药品先支持 1 张主图。
2. 图片字段允许为空，不影响药品新增、编辑、库存维护和用药计划。
3. 如果用户未上传图片，系统使用默认药品图片展示。
4. 图片仅作为识别辅助信息，不参与唯一性判断，也不参与库存逻辑。

默认图口径建议：

1. 后端允许 `drugImageUrl` 为空。
2. 返回药品详情或列表时，可额外提供 `displayDrugImageUrl`，优先取用户上传图，没有则回退到系统默认图。
3. 如果当前阶段后端暂不增加 `displayDrugImageUrl` 字段，也要统一约定由前端在 `drugImageUrl` 为空时展示默认图，避免不同页面各自兜底导致表现不一致。

这样做的价值：

1. 对用户更直观，尤其适合家庭常备药快速识别。
2. 不会把录入门槛抬高，愿意传图的用户可以增强辨识度，不愿意传图的用户也不受影响。
3. 后续如果要支持 OCR 识别包装信息或图片辅助搜药，也有扩展基础。

### 4.3 单位字典

建议新增或复用一套后台可维护的药品单位字典，至少包含：

1. `unitCode`
2. `unitName`
3. `unitCategory`
4. `status`
5. `sort`

推荐前端实际保存：

1. `stockUnitCode`
2. `stockUnitName`

这样做的好处：

1. 前端展示直接有名称。
2. 后端查询与校验有稳定编码。
3. 即使后续单位名称调整，历史数据仍可追溯原编码。

如果当前系统暂时只保存一个 `stockUnit` 文本字段，也可以先按以下方式兼容：

1. 前端从单位字典选择后，把 `unitName` 回填到 `stockUnit`
2. 后端先沿用文本存储
3. 后续再升级为 `code + name` 双字段

### 4.4 校验规则

建议当前阶段的校验规则为：

1. `drugName` 必填
2. 启用库存维护时，单位必填
3. 初始库存、预警值允许为空
4. 药品图片允许为空
5. 规格、厂家、通用名、剂型默认不强制
6. 药品名称在当前用户药柜内唯一

### 4.5 库存单位变更限制

单位一旦参与库存维护或服药扣减，就不建议随意修改。

建议规则：

1. 如果还没有库存记录，可以允许修改单位
2. 如果已经有库存或已存在绑定该药品的用药计划，则限制直接修改单位
3. 真正需要改单位时，后续再单独设计“单位迁移/库存换算”能力

这样可以避免出现：

1. 库存原来按“片”维护，后来被改成“盒”
2. 用药计划仍按“片”扣减，但药柜库存单位变成“盒”
3. 最终导致扣减和展示全部混乱


## 5. 前端交互建议

### 5.1 新增个人药品

默认表单只显示：

1. 药品名称
2. 单位选择
3. 初始库存
4. 预警值
5. 药品图片
6. 备注

折叠区域显示：

1. 规格
2. 厂家
3. 通用名
4. 剂型
5. 其他补充字段

图片交互建议：

1. 支持拍照、相册选择或已有上传组件复用。
2. 上传成功后回显缩略图，允许重新上传或删除。
3. 不上传图片时，不出现错误提示，也不阻断保存。
4. 没有上传图片时，表单和详情页直接展示默认药品图。

### 5.2 单位选择

前端支持：

1. 搜索
2. 下拉选择
3. 常用单位优先展示

不建议：

1. 允许自由文本输入单位

### 5.3 重名提示

当用户输入的药名已存在时：

1. 前端直接展示后端返回的唯一性提示
2. 引导用户在名称里补充规格或用途

示例：

1. `阿莫西林(0.25g)`
2. `阿莫西林-儿童备用`
3. `布洛芬-夜间用`


## 6. 与现有能力的关系

本次属于“当前阶段体验收敛”，不否定既有扩展方向。

保留的后续扩展能力包括：

1. 更完整的药品档案录入
2. 系统药品引入后自动带出规格厂家
3. 批号效期库存管理
4. 更细粒度的库存展示
5. 单位换算
6. 临期提醒
7. 药品图片 OCR 或图片辅助识别

因此这次不是回退能力，而是：

1. 当前默认交互先简化
2. 后端结构尽量不自断后路
3. 后续按业务成熟度逐步放开


## 7. 本次建议结论

建议当前阶段按以下方案落地：

1. 个人药柜新增药品默认只录“药品名称 + 单位”。
2. 单位由后台统一维护并下发，前端只允许选择和搜索。
3. 库存继续按用户选择的单位维护，不做换算。
4. 支持药品图片上传，但图片不是必填项。
5. 药品名称在当前用户药柜内唯一。
6. 遇到重名时，提示用户在名称中补充规格或用途区分。
7. 规格、厂家、通用名等字段先保留，但降级为非必填补充信息。
8. 单位变更要谨慎，已有库存或计划时不建议直接放开修改。

这套方案的优点是：

1. 用户录入成本低
2. 前端交互更简单
3. 图片能增强药品识别，但又不会变成录入阻碍
4. 后端仍保留后续扩展空间
5. 不会因为一次简化把后面可扩展能力全部锁死
