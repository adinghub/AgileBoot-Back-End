# 健康系统人员药品计划编码设计

## 1. 背景

当前健康系统的“家庭成员、药品、用药计划”在接口和 App 页面中主要暴露的是数据库主键 `memberId / drugId / planId`。  
这类主键虽然对程序内部关联足够稳定，但存在三个明显问题：

1. 对业务人员和终端用户可读性差，截图沟通时不直观。
2. App 直接显示内部主键，容易把技术实现细节暴露到业务界面。
3. 后续客服排障、运营核对、跨端对账时，缺少统一的业务标识。

因此本次改造目标是为三类核心对象补充独立业务编码，并让前端 / App 展示层优先展示编码而不是内部主键。

## 2. 目标

本次改造覆盖以下三个业务对象：

1. 家庭成员：新增 `memberCode`
2. 药品：新增 `drugCode`
3. 用药计划：新增 `planCode`

同时满足以下要求：

1. 新增数据自动生成编码
2. 历史数据可批量回填编码
3. 后端接口统一返回编码字段
4. 后台管理端列表优先展示编码
5. Flutter App 详情页和兜底文案优先展示编码

## 3. 编码规则

### 3.1 统一格式

编码统一采用：

`固定英文前缀 + 主键原值`

### 3.2 前缀定义

1. 家庭成员：`MBR`
2. 药品：`DRG`
3. 用药计划：`PLN`

### 3.3 示例

1. `memberId = 12` -> `MBR12`
2. `drugId = 3` -> `DRG3`
3. `planId = 105` -> `PLN105`

## 4. 方案取舍

### 4.1 为什么不引入独立号段表

本次没有引入单独的编码号段表，而是直接基于主键格式化，原因如下：

1. 历史数据回填成本最低，不需要额外迁移号段状态。
2. 新增流程简单，插入拿到主键后即可反写编码。
3. 运维排障时，编码和主键天然一一对应，便于快速定位。
4. 不补零后不存在固定长度上限问题，编码会随着主键自然增长。

### 4.2 为什么仍然单独落库编码

虽然编码可由主键推导，但仍选择单独落库，原因如下：

1. 前端和报表接口不需要重复拼装逻辑。
2. 后续如果编码规则变更，可以逐步迁移而不影响主键。
3. 数据导出、截图、SQL 排查都可以直接读取编码字段。

## 5. 数据库改造

### 5.1 MySQL

为以下表新增字段和唯一索引：

1. `health_family_member.member_code`
2. `health_drug.drug_code`
3. `health_medication_plan.plan_code`

### 5.2 PostgreSQL

为以下表新增字段和唯一索引：

1. `family_member.member_code`
2. `drug.drug_code`
3. `medication_plan.plan_code`

并提供单独增量脚本：

`sql/pgsql/健康系统_人员药品计划编码_20260426.sql`

该脚本负责：

1. 增列
2. 历史数据回填
3. 创建唯一索引

## 6. 后端实现

### 6.1 编码工具

新增统一工具类：

`healthtrail-domain/src/main/java/com/healthtrail/domain/health/support/HealthBizCodeFormatter.java`

职责：

1. 统一前缀定义
2. 统一前缀与拼接规则
3. 统一格式化入口

### 6.2 自动补码时机

新增数据采用以下流程：

1. 先插入主记录
2. 获取数据库主键
3. 根据主键生成业务编码
4. 立即回写到主表

这样可以避免在插入前“先猜编码”带来的并发和唯一性问题。

### 6.3 接口返回

以下核心 DTO 已补充编码字段：

1. `FamilyMemberDTO`
2. `HealthFamilyMemberAdminDTO`
3. `DrugDTO`
4. `MedicationPlanDTO`
5. `MedicationReminderDTO`
6. `MedicationReminderHistoryDTO`
7. `HealthHomeMemberCardDTO`
8. `HealthHomeReminderDTO`
9. `HealthHomeFollowUpItemDTO`

## 7. 前端与 App 展示

### 7.1 后台管理端

本次优先改造以下页面：

1. 系统药品列表：显示药品编码
2. 家庭共享成员列表与详情：显示成员编码
3. 用药历史列表：显示计划编码、成员编码

### 7.2 Flutter App

本次优先改造以下场景：

1. 用药计划详情：显示计划编码、成员编码、药品编码
2. 今日提醒详情：显示计划编码
3. 历史提醒详情：显示计划编码，成员兜底显示编码
4. 首页成员详情弹窗：显示成员编码
5. 首页提醒详情弹窗：显示成员编码
6. 工作台成员名称兜底：从 `成员#ID` 改为优先显示成员编码

## 8. 兼容策略

为避免灰度期间出现空白字段，本次所有展示层都采用“编码优先，主键兜底”的策略：

1. 后端若已回填编码，直接展示编码
2. 后端若历史数据暂未回填，服务层按主键规则即时格式化
3. App 模型层若收到空编码，也会退回格式化兜底字符串

## 9. 风险与后续建议

### 9.1 当前风险

1. 若旧环境未执行增量 SQL，相关字段不会真正入库。
2. 若部分边缘 DTO 仍只传 `memberId` 而未带 `memberCode`，个别页面可能仍会看到旧兜底文案。

### 9.2 后续建议

1. 将报告、消息、任务中心等涉及成员展示的 DTO 逐步统一补 `memberCode`。
2. 后台搜索能力后续可扩展为“按编码精确检索”。
3. 若未来出现跨系统对接需求，可在编码前缀层面继续扩展业务域区分。
