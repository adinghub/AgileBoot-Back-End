# 药品双层药品库设计

## 1. 功能目标

为了解决“后台需要统一下发常用药”和“用户又需要自行补充家庭药品”这两个场景，本次药品模块采用双层药品库设计。

目标如下：

1. 后台可维护系统下发药品
2. App 用户可维护自己的个人药品
3. App 创建用药计划时可以同时选系统药品和个人药品
4. 两类药品边界清晰，避免互相越权操作


## 2. 核心设计

### 2.1 归属规则

`health_drug.owner_user_id` 作为药品归属字段：

1. `0`：系统下发药品
2. `当前 App 用户ID`：个人药品

### 2.2 查询规则

1. App 药品列表：查询“系统药品 + 当前用户个人药品”
2. App 药品详情：允许查看“系统药品 + 当前用户个人药品”
3. 后台药品列表：只查询系统药品
4. 后台药品详情：只查询系统药品

### 2.3 编辑规则

1. App 新增：只能新增自己的个人药品
2. App 修改/删除：只能操作自己的个人药品
3. 后台新增：新增系统下发药品
4. 后台修改/删除：只能操作系统下发药品

### 2.4 用药计划规则

创建或修改用药计划时，药品来源允许三种：

1. 系统下发药品
2. 当前用户自己的个人药品
3. 手工填写 `customDrugName`


## 3. 接口影响

### 3.1 App 端

`GET /app/drugs` 返回时需要区分药品来源：

1. `ownerUserId = 0`
2. `systemDrug = true`

前端可据此把系统药品做成只读标签或不可编辑状态。

### 3.2 后台端

新增后台接口：

1. `GET /health/drugs`
2. `GET /health/drugs/{drugId}`
3. `POST /health/drugs`
4. `PUT /health/drugs/{drugId}`
5. `DELETE /health/drugs/{drugId}`


## 4. 数据脚本说明

本次直接替换药品初始化脚本，不新增迁移脚本。

原因：

1. 当前你还没有执行 SQL
2. 直接替换初始化脚本最干净
3. 后续建库时就会直接得到双层药品库结构
