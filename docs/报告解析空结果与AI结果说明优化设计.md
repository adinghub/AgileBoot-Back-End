# 报告解析空结果与 AI 结果说明优化设计

## 1. 背景问题

本次联调里出现了两个容易误导排查的现象：

1. 后端日志显示：
   - `报告图片 AI 视觉结构化未产出指标`
   - `体检报告文件解析完成，结构化指标数：0`
2. 但前端详情页里仍然能看到报告指标。

与此同时，业务侧还提出了新的文案诉求：

1. 指标结果说明不要只解释“这个指标是什么”；
2. 还要结合本次结果给出简短、克制、专业的提示；
3. 可以提醒用户结合医生诊断，但不能输出诊疗结论。


## 2. 排查结论

### 2.1 为什么日志是 0 条，页面却还能看到指标

这次现象的根因不是日志打印错误，而是当前系统的既有保存策略。

现有逻辑是：

1. 解析出 `parsedItems`
2. 只有 `parsedItems` 非空时，才删除旧的 `report_item`
3. 再保存新的 `report_item`

因此当一份报告：

1. 之前已经有历史解析指标；
2. 本次重新解析结果为 0 条；

就会出现：

1. 本次日志真实记录为 0 条；
2. 详情页继续读到历史旧指标。

也就是说，这是“旧结果仍然保留”的状态表现，不是“本次其实识别成功但日志写错了”。

本次按你的要求，只保留这个排查结论，不修改现有行为。

### 2.2 AI 总结是否把图片链接传给大模型

需要区分两条链路：

1. 视觉结构化解析
2. AI 总结

#### 视觉结构化解析链路

视觉结构化解析没有把公网图片链接传给大模型。

当前实现是：

1. 后端先读取报告文件字节；
2. 在 `HealthReportFileParser#buildImageDataUrl(...)` 中转成 `data:image/...;base64,...`
3. 通过 `HealthReportExternalLlmClient#generateTextWithImage(...)` 发送给模型。

结论：

1. 发的是文件内容的 Base64 data URL；
2. 不是 MinIO / OSS 外链；
3. 不依赖模型服务回源访问图片地址。

#### AI 总结链路

当前 AI 总结没有把图片链接发给大模型，也没有直接再发一次原始文件。

它当前发送的是结构化上下文，包括：

1. 报告名称、日期、类型
2. 分析摘要
3. 异常项
4. 建议项
5. 趋势项

所以当前总结链路属于：

1. 基于结构化结果的二次总结；
2. 不是基于原始文件直读的多模态总结。


## 3. 本次改动范围

本次只调整 AI 文案能力，不改“空解析结果保留旧指标”的既有行为。

### 3.0 增补大模型调用日志

为了方便联调和线上排查，本次额外在 `HealthReportExternalLlmClient` 中补了统一调用日志。

现在会固定输出三类日志：

1. 开始调用
2. 调用结果摘要
3. 调用结束

日志中会包含：

1. `scene`
2. `provider`
3. `model`
4. `systemPromptLength`
5. `userContentPreview`
6. `responsePreview`
7. `durationMs`

其中多模态日志不会打印完整图片 Base64，只会打印：

1. 是否是 data URL
2. 图片数据长度
3. 文本预览摘要

这样既能看清调用链路，又不会把超长图片数据直接刷进日志。

### 3.0.1 增强结构化 JSON 收口能力

联调日志显示，部分视觉模型虽然最终给了结构化结果，但返回体前面会带一段 `<think>...</think>` 思考文本。

旧逻辑只要看到“返回内容不是纯 JSON”，就可能把这次结果误判成：

1. `未识别出可用指标`
2. `结果格式不正确`

因此本次在 `HealthReportAiStructuredParser` 中补了一层收口逻辑：

1. 先去掉 markdown fence；
2. 再去掉 `<think>...</think>` 思考块；
3. 最后从混合文本中提取第一段结构完整的 JSON 对象。

这样当模型返回“思考内容 + JSON”时，后端仍然可以正确消费真正的结构化结果。

### 3.0.2 对结构化场景显式要求 JSON 输出

除了提示词里写“严格返回 JSON”，本次还在客户端请求层增加了显式输出约束：

1. 文本结构化调用使用 `generateJsonText(...)`
2. 视觉结构化调用使用 `generateJsonTextWithImage(...)`
3. 批量指标结果说明回填也使用 `generateJsonText(...)`

这些调用会在请求体里附带：

```json
{
  "response_format": {
    "type": "json_object"
  }
}
```

这样做的目的不是完全替代后端 JSON 清洗，而是双保险：

1. 先从请求侧尽量减少模型输出思考过程和额外说明；
2. 再从后端解析侧兜底处理少量不规范返回。

### 3.1 结构化解析阶段的 `itemInterpretation`

调整 `HealthReportAiStructuredParser` 提示词：

1. 不再只要求解释指标含义；
2. 改为“先解释指标主要反映什么，再结合本次结果和参考范围给出克制提示”；
3. 明确允许提示结合医生诊断或按需复查；
4. 明确禁止诊断结论和治疗方案。

### 3.2 行级指标结果说明生成

调整 `HealthReportItemInterpretationGenerator`：

1. 输入里新增 `resultValue`、`abnormalFlagName`；
2. 让模型知道当前结果值和异常方向；
3. 输出从“指标含义解释”升级为“指标结果说明”；
4. 文案要求更短、更准、更贴近用户阅读。

### 3.3 报告级结果解读与 AI 总结

同时收紧了两处整体文案口径：

1. `HealthReportResultInterpretationGenerator`
2. `HealthReportApplicationService` 中的外部 AI 总结提示词

核心目标：

1. 少说空话；
2. 尽量结合具体指标值；
3. 保持专业、克制、便于普通用户理解；
4. 可以提醒结合医生诊断，但不输出诊疗方案。


## 4. 预期效果

本次改动完成后，预期会有三点改善：

1. 指标说明不再只讲抽象定义，而会结合本次结果做克制提示；
2. 报告级解读和 AI 总结会更具体，不再只有泛泛而谈的建议；
3. 整体输出风格会更短、更专业、更适合普通用户直接阅读。


## 5. 验证建议

建议重点验证以下几类指标：

1. 正常值指标：确认不会被写成“异常”，但仍能解释其意义；
2. 偏高/偏低指标：确认会结合当前结果值给出简短提示；
3. 无参考范围指标：确认不会编造阈值；
4. AI 总结：确认会引用具体结果，不再只是“建议关注、建议复查”。
