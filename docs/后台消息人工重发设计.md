# 后台消息人工重发设计

## 1. 功能目标

当前系统已经支持：

1. App 消息中心落库
2. 后台消息审计列表与详情
3. 用药提醒与报告建议 Push 派发

但在实际运行中，仍然会遇到这类场景：

1. 用户首次接收时没有注册设备
2. 首次 Push 发送失败
3. 客服或运营确认需要补发一次通知

因此本期补充后台人工重发能力，让后台可以对单条消息执行一次人工补发，并把结果继续回写到原消息记录中。


## 2. 设计原则

### 2.1 不新建消息，直接重发原消息

人工重发不会新建第二条消息记录，
而是直接复用原有 `health_app_message` 中已经保存的：

1. 标题
2. 正文
3. 业务透传载荷
4. 归属用户

这样可以保证：

1. 去重链路不被打乱
2. 审计轨迹集中在同一条消息上
3. 后台更容易理解“这条消息累计被发过多少次”

### 2.2 重发链路与原始业务发送器解耦

后台人工重发不再回到：

1. 用药提醒发送器
2. 报告建议发送器

重新还原原始业务对象，
而是新增消息模块自己的发送器，直接消费消息表中的标准化数据。

这样后续无论消息来源是什么业务场景，
后台都能统一重发。

### 2.3 重发结果必须回写原消息状态

每次人工重发后，仍然回写：

1. `send_status`
2. `send_time`
3. `send_channel`
4. `send_retry_count`
5. `send_result_message`

这样消息详情里可以持续看到最新一次重发结果。


## 3. 接口设计

新增后台接口：

`POST /health/messages/{messageId}/resend`

当前设计为：

1. 只支持单条重发
2. 不支持批量重发
3. 不要求请求体


## 4. 业务规则

### 4.1 允许重发的消息

当前只要消息记录存在，且具备以下基础字段，就允许重发：

1. `owner_user_id`
2. `message_title` 或 `message_content`

如果缺少必要字段，则直接返回业务异常。

### 4.2 无可用设备时的处理

若当前用户没有可用设备 Token：

1. 接口不会报系统异常
2. 会把本次结果按发送失败回写到消息表
3. 返回明确的失败说明给后台

### 4.3 当前仍是单通道重发

本期人工重发仍只走：

`APP_PUSH`

后续如果需要接入站内信、短信或厂商多通道，
可以继续扩展消息模块发送器，而不影响后台接口层。


## 5. 后续建议

建议下一步继续补：

1. 仅对失败消息开放重发按钮
2. 重发前增加操作确认文案
3. 重发操作统计与告警
4. 批量重发与异步任务化
