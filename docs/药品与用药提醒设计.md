# 药品与用药提醒设计

## 1. 目标

本次设计用于支撑健康系统一期里最核心的高频能力：

1. 药品查询
2. 用药计划
3. 今日提醒
4. 服药反馈

当前版本的药品采用“双层药品库”方式：

1. 后台可以维护系统下发药品
2. App 用户也可以维护自己的个人药品
3. 用药计划既能选系统药品，也能选个人药品，还能临时填写自定义药名


## 2. 模块拆分

### 2.1 药品模块

药品模块承担“双层药品库”职责。

当前能力：

1. App 端分页查询“系统药品 + 自己的药品”
2. App 端查看系统药品详情和自己的药品详情
3. App 端新增自己的药品
4. App 端修改自己的药品
5. App 端删除自己的药品
6. 后台分页查询系统下发药品
7. 后台新增系统下发药品
8. 后台修改系统下发药品
9. 后台删除系统下发药品

### 2.2 用药计划模块

用药计划描述的是一条长期或短期的提醒规则。

例如：

1. 某个家庭成员
2. 某个药品
3. 从哪天开始到哪天结束
4. 每天几点提醒
5. 每次吃多少
6. 饭前还是饭后
7. 每周哪几天提醒
8. 每隔几小时提醒

### 2.3 用药提醒记录模块

提醒记录是计划的执行结果明细。

它不是规则，而是规则在某一个具体时间点生成的一次提醒实例。

例如：

1. 2026-04-23 08:00 这一次提醒
2. 当前状态是待处理、已服药、已跳过还是已过期

### 2.4 历史服药与依从率模块

在今日提醒之外，系统还继续补齐了历史记录与依从率分析能力。

当前能力：

1. 历史服药记录列表
2. 用药依从率统计
3. 用药趋势分析
4. 后台用药历史与依从率管理

## 4. 关键业务规则

### 4.1 药品必须来自“系统药品 / 当前用户自己的药品”或自定义药名

用药计划创建时：

1. 如果选择系统下发药品，则保存 `drug_id`
2. 如果选择当前用户自己的药品，则保存 `drug_id`
3. 如果没有选择任何药品，则必须填写 `custom_drug_name`

这样既支持后台统一维护公共药品，也支持用户维护自己的药品库，还允许临时补充个性化药品信息。

### 4.2 用药计划必须绑定家庭成员

后续提醒、报告、药物统计等健康业务都要围绕成员维度展开，因此用药计划必须关联到家庭成员。

### 4.3 创建和修改计划时自动生成未来提醒

当前实现采用“计划驱动提醒记录”的方式：

1. 创建计划后立即生成未来提醒
2. 修改计划后重建未来提醒
3. 不回补历史提醒，避免影响已经产生的历史记录

### 4.4 提醒生成规则支持多种频率

当前计划生成提醒时，已经支持以下频率模型：

1. 每日提醒
2. 每周固定日期提醒
3. 每隔几小时提醒

这样可以覆盖用户最常见的慢病、短疗程和间隔服药场景。

### 4.5 只允许处理待处理提醒

为了保证提醒状态流转清晰：

1. 只有 `待处理` 状态允许标记为 `已服药`
2. 只有 `待处理` 状态允许标记为 `已跳过`
3. 已过期、已服药、已跳过状态不允许重复处理

### 4.6 今日提醒查询前自动过期旧提醒

当前用户查询今日提醒前，系统会先把过点但未处理的旧提醒统一更新成 `已过期`。

这样前端展示的状态更加一致。

### 4.7 到点提醒支持派发与消息联动

当前系统已经补齐到点提醒派发链路：

1. 定时任务扫描即将到点或已到点提醒
2. 写入消息中心记录
3. 按设备 Token 调用 Push 通道派发
4. 回写提醒与消息的发送结果

## 6. 一期能力边界

当前实现边界如下：

1. 药品支持后台下发系统药品，也支持 App 用户自己维护个人药品
2. 用药计划支持 CRUD
3. 用药计划支持按 `DAILY`、`WEEKLY`、`INTERVAL_HOURS` 等频率生成提醒
4. 今日提醒与历史服药记录都支持查询
5. 提醒支持标记已服药和已跳过
6. 系统支持自动过期、未来提醒补齐、到点派发与消息联动
7. App 支持设备注册并按设备 Token 派发提醒
8. 已提供用药依从率统计与趋势分析

当前仍未覆盖：

1. 系统药品分级推送与个人药品快速引用
2. 用户药品导入与一键复制常用计划
