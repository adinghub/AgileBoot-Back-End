# 后台消息审计设计

## 1. 功能目标

当前健康系统已经具备：

1. App 消息中心落库
2. 用药提醒 Push 派发
3. 报告建议 Push 派发
4. 消息已读与未读状态

但后台目前还缺少统一的审计入口，导致出现以下问题时不方便排查：

1. 某个用户说自己没有收到提醒
2. 某份报告为什么重复或没有生成消息
3. 某条消息是否已经发送成功
4. App 端点击消息后理论上应该跳到哪里

因此本期补充后台消息审计能力，让后台可以统一查看消息中心实际落库结果和最近一次 Push 派发状态。


## 2. 设计原则

### 2.1 直接复用消息中心表，不新增冗余审计表

后台审计直接复用：

`health_app_message`

原因是当前消息中心表已经完整保存了：

1. 业务场景
2. 业务主键
3. 标题正文
4. 发送状态
5. 已读状态
6. 去重键
7. 业务载荷

因此后台只需要基于现有表做查询封装即可。

### 2.2 先做审计与单条补救，不直接开放批量重发

本期后台当前开放：

1. 列表
2. 详情
3. 单条人工重发

暂不开放：

1. 批量重发
2. 删除消息
3. 修改已读状态

原因是更重操作会涉及更多边界：

1. 是否绕过去重
2. 是否记录二次审计日志
3. 是否会误打扰用户

因此当前先把“查清楚发生了什么”做好。


## 3. 查询范围

### 3.1 列表筛选项

后台列表当前支持：

1. `ownerUserId`
2. `memberId`
3. `businessScene`
4. `businessId`
5. `readStatus`
6. `sendStatus`
7. `dedupKey`
8. `keyword`
9. `createTime` 时间范围

其中 `keyword` 当前匹配：

1. 消息标题
2. 消息正文
3. 成员名称快照

### 3.2 排序规则

后台列表默认按：

1. `message_id` 倒序

这样更方便先看到最新消息。


## 4. 返回结构设计

### 4.1 列表

后台列表在 App 端消息列表基础上，额外补充：

1. App 用户ID
2. App 用户手机号
3. App 用户昵称
4. 去重键
5. 发送通道
6. 发送结果说明

### 4.2 详情

后台详情进一步补充：

1. 原始 `payloadJson`
2. 解析后的 `payload`

这样后台既能看到原始落库值，
也能直接看到结构化后的跳转参数与推荐动作。


## 5. 接口设计

后台消息审计接口：

1. `GET /health/messages`
2. `GET /health/messages/{messageId}`
3. `POST /health/messages/{messageId}/resend`
4. `POST /health/messages/batch-resend`
5. `GET /health/messages/statistics`

建议下一步继续补：

2. 后台与首页未读角标数据联动监控

4. 统计结果缓存化
