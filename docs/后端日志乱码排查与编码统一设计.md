# 后端日志乱码排查与编码统一设计

## 1. 问题背景

近期在 `REPORT_FOLLOW_UP` 相关日志中，控制台输出出现了大量 `?????`，例如：

- `messageTitle`
- `messageContent`
- `targetAnchorName`
- `recommendedAction.riskLevelName`

同时还伴随一条额外报错：

- `could not found i18nMessage entry for key: Business.USER_FAIL_TO_GET_USER_INFO`

这会让开发人员误以为：

1. 中文内容在业务层已经被破坏；
2. JSON 序列化存在字符集问题；
3. 数据库存储了乱码；
4. 国际化资源没有生效。

## 2. 排查结论

本次排查后的结论如下：

1. 落盘日志 `D:\logs\healthtrail-api-dev\sys-info.log` 中中文内容是正常的。
2. 历史文件日志已经可以正确显示诸如“本人”“用药提醒处理页”“提醒反馈区”等中文字段。
3. 说明业务对象构造、Jackson 序列化、数据库读写主链路没有把中文变成问号。
4. 当前“乱码”主要集中在控制台展示链路，更准确地说是“控制台编码与日志输出编码未统一”。
5. 同时，`Business.USER_FAIL_TO_GET_USER_INFO` 在 `messages.properties` / `messages_en.properties` 中缺失，导致 `ApiException` 回退打印缺失键错误日志。

## 3. 根因分析

### 3.1 控制台乱码根因

`logback-spring.xml` 中各个 `encoder` 之前没有显式声明 `charset`。

这意味着：

1. Logback 会依赖运行环境默认字符集；
2. Windows PowerShell、IDEA 运行控制台、Maven `spring-boot:run`、直接执行 Jar 时的默认编码可能不同；
3. 当控制台链路不按 UTF-8 解释中文时，就会出现问号或乱码。

需要特别注意：

1. “文件日志正常、控制台乱码”是这类问题的典型表现；
2. 这不代表数据库或业务字符串已经损坏；
3. 也不代表 JSON 负载本身是错的。

### 3.2 i18n 报错根因

`ErrorCode.Business.USER_FAIL_TO_GET_USER_INFO` 已经声明了 i18n key：

- `Business.USER_FAIL_TO_GET_USER_INFO`

但资源文件中没有对应键值，导致 `ApiException#fillErrorCode` 调用 `MessageUtils.message(...)` 时抛异常，随后记录：

- `could not found i18nMessage entry for key: Business.USER_FAIL_TO_GET_USER_INFO`

这条错误虽然不是乱码根因，但会污染日志，干扰开发人员定位真正问题。

## 4. 本次改动

### 4.1 日志编码统一

在 `healthtrail-infrastructure/src/main/resources/logback-spring.xml` 中做了以下处理：

1. 新增统一属性 `log.charset=UTF-8`；
2. 为 `console` appender 的 `encoder` 显式添加 `<charset>UTF-8</charset>`；
3. 为 `info_log`、`error_log`、`debug_log` 三个文件 appender 的 `encoder` 全部显式添加 UTF-8。

这样做的目的：

1. 让控制台和文件日志都按同一编码输出；
2. 减少不同开发机、不同启动姿势带来的差异；
3. 后续排查中文日志问题时，优先排除“Logback 未声明编码”这个不确定因素。

### 4.2 补齐缺失国际化键

在中英文消息资源中补充：

- `Business.USER_FAIL_TO_GET_USER_INFO`

这样可以避免异常处理阶段重复打印“缺少 i18n key”的错误日志。

## 5. 仍需开发环境配合的事项

即使后端已经强制按 UTF-8 输出，如果终端程序本身不是 UTF-8，控制台仍然可能显示异常。

建议开发环境统一做以下配置：

1. Windows PowerShell / CMD 启动前执行 `chcp 65001`；
2. IDEA 运行配置与编辑器编码统一设置为 `UTF-8`；
3. 如通过 JVM 参数自定义编码，确保包含 `-Dfile.encoding=UTF-8`；
4. 排查日志时优先对照落盘日志文件，而不是只看控制台截图。

## 6. 验证方式

建议用以下场景回归：

1. 重新触发一条中文消息通知，例如报告跟进或用药提醒；
2. 同时观察 IDEA / PowerShell 控制台输出；
3. 打开 `D:\logs\healthtrail-api-dev\sys-info.log` 对照同一条记录；
4. 确认 `messageTitle`、`messageContent`、`targetAnchorName`、`riskLevelName` 等字段均为正常中文；
5. 确认不再出现 `Business.USER_FAIL_TO_GET_USER_INFO` 缺失键日志。

## 7. 风险说明

本次改动风险较低，原因如下：

1. 没有调整业务字段含义；
2. 没有修改数据库结构；
3. 只统一了日志输出编码；
4. 只补齐了原本就应存在的国际化资源键。

唯一需要注意的是：

1. 如果某些外部脚本历史上依赖“平台默认编码”读取日志文件，改成显式 UTF-8 后需要同步确认脚本读取方式；
2. 但从当前项目的中文业务背景来看，统一到 UTF-8 是更安全、更可维护的方案。
