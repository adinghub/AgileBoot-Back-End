# 用药提醒发送通道设计

## 1. 设计目标

在前一阶段已经补上“提醒自动生成”和“提醒自动过期”以后，下一步核心问题就是：

1. 提醒记录已经存在
2. 但系统还没有真正的“发送状态”概念
3. 后续接 App Push、站内信、短信时缺少统一扩展点

因此本次补充提醒发送通道底座，先把发送链路和状态管理打通。


## 2. 本次落地范围

### 2.1 提醒表增加发送字段

在 `health_medication_reminder` 中新增：

1. `notify_status`：发送状态
2. `notify_time`：最近一次发送时间
3. `notify_fail_reason`：发送失败原因
4. `notify_retry_count`：发送重试次数

### 2.2 增加发送状态枚举

发送状态与业务提醒状态分离：

1. 业务状态：待处理、已服药、已跳过、已过期
2. 发送状态：待发送、发送成功、发送失败

这样就能准确区分：

1. 提醒是否已经发给用户
2. 用户是否真正处理了提醒

### 2.3 增加统一发送器接口

新增 `MedicationReminderNotifier` 作为发送通道扩展点。

当前默认实现：

1. 基于用户设备表读取活跃设备
2. 按设备 Token 逐条模拟发送
3. 发送成功后回写发送状态
4. 失败时记录失败原因并累计重试次数

后续如果接入真实推送，只需要新增新的发送器实现即可。

### 2.4 增加派发定时任务

新增“到点提醒派发任务”：

1. 默认每分钟执行一次
2. 查询已到提醒时间、仍待处理、尚未发送成功的提醒
3. 交给发送器派发
4. 按结果回写发送状态


## 3. 关键设计点

### 3.1 发送器与业务层解耦

应用服务只负责：

1. 找出应该发送的提醒
2. 构造标准化提醒载荷
3. 回写发送结果

真正如何发送，由 `MedicationReminderNotifier` 决定。

这样后续可平滑支持：

1. App Push
2. 站内信
3. 短信
4. 微信模板消息

### 3.2 默认实现先走日志模拟

当前阶段已经补上设备 Token 数据源，但还没有接入真实厂商 SDK。

因此本次先用“按设备维度日志模拟发送”的方式把链路打通，保证：

1. 数据模型正确
2. 设备绑定关系正确
3. 调度逻辑正确
4. 状态流转正确

### 3.3 发送失败支持有限次重试

当前默认策略：

1. 每条提醒默认最多重试 3 次
2. 超过最大重试次数后，不再继续自动派发
3. 失败原因会保存在提醒记录中，方便排查


## 4. 当前默认调度配置

当前默认参数：

1. 派发 cron：每分钟一次
2. 单次批大小：100 条
3. 最大重试次数：3 次

后续可通过配置覆盖：

1. `health.medication.reminder.schedule.dispatch-cron`
2. `health.medication.reminder.schedule.dispatch-batch-size`
3. `health.medication.reminder.schedule.notify-max-retry-count`
