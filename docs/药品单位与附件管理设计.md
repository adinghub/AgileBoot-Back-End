# 药品单位与附件管理设计

## 1. 设计目标

本次药品能力调整，目标是把“个人药柜简化录入、系统药品引入、库存批号效期管理、药品图片非强制上传、后台统一维护单位”统一收口到一套最终实现口径。

当前确认的核心原则如下：

1. 药品表名直接使用 `drug`，不再使用任何 `health_*` 前缀。
2. 药品主表不保存汇总库存，库存通过批号效期库存实时计算。
3. 药品与批号效期库存是 `1 -> N` 关系。
4. 药品图片可选上传，未上传时统一返回默认图片。
5. 药品单位由后台维护并下发，前端只负责搜索和选择。
6. 当前保留既有药品扩展字段，产品主流程先收敛到“名称 + 单位 + 可选库存”。


## 2. 最终业务口径

### 2.1 药品主档

`drug` 负责保存药品主档信息，分为两类：

1. 系统药品：`owner_user_id = 0`
2. 个人药品：`owner_user_id = 当前 App 用户 ID`

个人药品支持两种来源：

1. 用户手工新增
2. 从系统药品引入后生成个人独立副本

引入后的个人药品与系统药品解耦，后续库存、备注、预警值、图片都独立维护。

### 2.2 批号效期库存

`drug_stock_batch` 负责保存库存明细：

1. `drug_id` 关联药品主档
2. `batch_no` 允许为空
3. `expire_date` 必填
4. `stock_quantity` 保存该批次当前库存

展示和扣减统一遵循同一套排序规则：

1. 效期早的优先
2. 批号为空的排前面
3. 最后按批次 ID 兜底，保证顺序稳定

这样可以确保前端看到的批次顺序和后端扣减顺序完全一致。

### 2.3 库存日志

`drug_stock_log` 保存库存变更轨迹，用于追踪以下动作：

1. 新增药品时初始化库存
2. 引入系统药品时初始化库存
3. 手工补库存
4. 修改预警值
5. 标记已服药后的自动扣减

### 2.4 单位主数据

`drug_unit` 是后台统一维护的药品单位表，前端只能搜索和选择，不能自由输入。

当前实现同时保存：

1. `stock_unit_id`：关联标准单位
2. `stock_unit`：写入当时的单位名称快照

这样可以在当前阶段兼容既有代码，同时为后续彻底收敛到标准主数据预留空间。

### 2.5 附件主数据

药品图片和单位图标统一收口到 `attachment` 表，不再单独设计 `drug_attachment`。

当前支持两种附件类型：

1. `DRUG_IMAGE`：药品图片
2. `DRUG_UNIT_ICON`：药品单位图标

这样设计的好处是：

1. 业务表只保存附件 ID，不直接耦合文件路径
2. 后续从本地存储切换到 OSS / MinIO 时改动更小
3. 未来如果其他业务也需要图片或文件，可以直接复用 `attachment`


## 3. 当前前后端交互口径

### 3.1 手工新增个人药品

当前主流程建议前端只强制用户填写：

1. `drugName`
2. `stockUnitId`

其余字段可选：

1. `stockQuantity`
2. `batchNo`
3. `expireDate`
4. `stockAlertThreshold`
5. `remark`
6. `imageAttachmentId`

保留但默认放到补充信息区的字段：

1. `genericName`
2. `brandName`
3. `dosageForm`
4. `specification`
5. `manufacturer`
6. `indication`
7. `usageInstruction`
8. `adverseReaction`
9. `contraindication`

### 3.2 引入系统药品

引入系统药品时，当前允许用户同时补充或修改：

1. 个人药柜中的显示名称
2. 首批库存
3. 批号
4. 效期
5. 库存预警值
6. 库存单位
7. 药品图片
8. 备注

这样系统药品“拿来即用”，不需要用户引入后再二次编辑库存。

### 3.3 药品名称唯一性

当前唯一性规则为：

1. 同一 `owner_user_id` 下，`drug_name` 唯一
2. 系统药品和个人药品彼此不冲突
3. 重名提示文案统一为：`药品名称已存在，可补充规格/备注区分`

### 3.4 默认图片口径

药品图片不是必填项。

如果未上传图片：

1. 数据库允许 `image_attachment_id` 为空
2. 接口统一返回默认图片地址 `/images/drug-default.svg`
3. 前端不需要自己再做多套空值兜底


## 4. 最终表设计

以下表结构与当前初始化脚本 `sql/pgsql/健康系统_schema_20260423.sql` 保持一致。

### 4.1 附件表 `attachment`

```sql
CREATE TABLE IF NOT EXISTS attachment (
    attachment_id BIGSERIAL PRIMARY KEY,
    owner_user_id BIGINT,
    attachment_type VARCHAR(30) NOT NULL,
    storage_provider VARCHAR(30) DEFAULT 'LOCAL' NOT NULL,
    file_url VARCHAR(500) NOT NULL,
    stored_file_name VARCHAR(255) NOT NULL,
    original_file_name VARCHAR(255),
    file_size BIGINT,
    file_extension VARCHAR(20),
    content_type VARCHAR(100),
    status SMALLINT DEFAULT 1 NOT NULL,
    remark VARCHAR(500),
    creator_id BIGINT,
    create_time TIMESTAMPTZ,
    updater_id BIGINT,
    update_time TIMESTAMPTZ,
    deleted SMALLINT DEFAULT 0 NOT NULL
);
```

字段说明：

1. `owner_user_id`：App 用户上传时回填用户 ID，后台上传时允许为空
2. `attachment_type`：附件类型，当前只允许 `DRUG_IMAGE`、`DRUG_UNIT_ICON`
3. `file_url`：当前保存相对访问路径

### 4.2 药品单位表 `drug_unit`

```sql
CREATE TABLE IF NOT EXISTS drug_unit (
    unit_id BIGSERIAL PRIMARY KEY,
    unit_code VARCHAR(50) NOT NULL,
    unit_name VARCHAR(20) NOT NULL,
    unit_alias VARCHAR(200),
    precision_scale SMALLINT DEFAULT 0 NOT NULL,
    sort INT DEFAULT 0 NOT NULL,
    status SMALLINT DEFAULT 1 NOT NULL,
    icon_attachment_id BIGINT,
    remark VARCHAR(500),
    creator_id BIGINT,
    create_time TIMESTAMPTZ,
    updater_id BIGINT,
    update_time TIMESTAMPTZ,
    deleted SMALLINT DEFAULT 0 NOT NULL,
    CONSTRAINT uk_drug_unit_code UNIQUE (unit_code, deleted),
    CONSTRAINT uk_drug_unit_name UNIQUE (unit_name, deleted)
);
```

字段说明：

1. `unit_code`：系统稳定识别编码
2. `unit_name`：前端主展示值
3. `unit_alias`：搜索增强字段
4. `precision_scale`：库存数量允许的小数位
5. `icon_attachment_id`：单位图标附件，可为空

### 4.3 药品主表 `drug`

```sql
CREATE TABLE IF NOT EXISTS drug (
    drug_id BIGSERIAL PRIMARY KEY,
    owner_user_id BIGINT NOT NULL,
    drug_name VARCHAR(100) NOT NULL,
    generic_name VARCHAR(100),
    brand_name VARCHAR(100),
    dosage_form VARCHAR(50),
    specification VARCHAR(100),
    indication VARCHAR(1000),
    usage_instruction VARCHAR(1000),
    adverse_reaction VARCHAR(1000),
    contraindication VARCHAR(1000),
    manufacturer VARCHAR(200),
    drug_type VARCHAR(20),
    source_drug_id BIGINT,
    stock_unit_id BIGINT,
    stock_unit VARCHAR(20),
    image_attachment_id BIGINT,
    stock_alert_threshold NUMERIC(10, 2),
    low_stock_notified SMALLINT DEFAULT 0 NOT NULL,
    low_stock_notify_time TIMESTAMPTZ,
    status SMALLINT DEFAULT 1 NOT NULL,
    remark VARCHAR(500),
    creator_id BIGINT,
    create_time TIMESTAMPTZ,
    updater_id BIGINT,
    update_time TIMESTAMPTZ,
    deleted SMALLINT DEFAULT 0 NOT NULL,
    CONSTRAINT uk_drug_owner_name UNIQUE (owner_user_id, drug_name)
);
```

字段说明：

1. `source_drug_id`：个人药品来源系统药品 ID，引入系统药品时使用
2. `stock_unit_id`：标准单位 ID
3. `stock_unit`：单位名称快照
4. `image_attachment_id`：药品图片附件 ID
5. `stock_alert_threshold`：自定义库存预警值
6. `low_stock_notified` / `low_stock_notify_time`：当前预警周期状态

注意：

1. `drug` 不保存汇总库存
2. 药品库存统一通过 `SUM(drug_stock_batch.stock_quantity)` 实时计算

### 4.4 批号效期库存表 `drug_stock_batch`

```sql
CREATE TABLE IF NOT EXISTS drug_stock_batch (
    batch_id BIGSERIAL PRIMARY KEY,
    owner_user_id BIGINT NOT NULL,
    drug_id BIGINT NOT NULL,
    batch_no VARCHAR(50),
    expire_date DATE NOT NULL,
    stock_quantity NUMERIC(10, 2) NOT NULL,
    creator_id BIGINT,
    create_time TIMESTAMPTZ,
    updater_id BIGINT,
    update_time TIMESTAMPTZ,
    deleted SMALLINT DEFAULT 0 NOT NULL
);
```

字段说明：

1. `batch_no` 允许为空，满足“用户记不清批号也能维护库存”的场景
2. `expire_date` 必填，确保批次排序和临期能力可用

### 4.5 库存日志表 `drug_stock_log`

```sql
CREATE TABLE IF NOT EXISTS drug_stock_log (
    log_id BIGSERIAL PRIMARY KEY,
    owner_user_id BIGINT NOT NULL,
    drug_id BIGINT NOT NULL,
    change_type VARCHAR(30) NOT NULL,
    before_quantity NUMERIC(10, 2),
    change_quantity NUMERIC(10, 2),
    after_quantity NUMERIC(10, 2),
    stock_unit_snapshot VARCHAR(20),
    alert_threshold_snapshot NUMERIC(10, 2),
    related_plan_id BIGINT,
    related_reminder_id BIGINT,
    operation_remark VARCHAR(255),
    creator_id BIGINT,
    create_time TIMESTAMPTZ,
    updater_id BIGINT,
    update_time TIMESTAMPTZ,
    deleted SMALLINT DEFAULT 0 NOT NULL
);
```


## 5. 后端实现要点

### 5.1 附件上传

当前已提供两套上传入口：

1. 后台：`AttachmentController`
   路径：`/health/attachments/upload`
2. App：`AppAttachmentController`
   路径：`/app/attachments/upload`

返回结果统一是附件 DTO，前端后续在新增或编辑药品、药品单位时只需要回传附件 ID。

### 5.2 单位管理

当前已提供：

1. 后台药品单位 CRUD：`DrugUnitAdminController`
2. App 单位列表查询：`DrugUnitController`

应用层会校验：

1. 单位名称必填
2. 单位编码唯一
3. 单位名称唯一
4. 停用单位不能被药品录入使用
5. 已被药品引用的单位不能直接删除

### 5.3 药品录入与库存维护

`DrugApplicationService` 当前负责以下关键规则：

1. 把 `stockUnitId` 解析成 `stockUnit` 快照
2. 校验药品图片附件必须是 `DRUG_IMAGE`
3. 读取药品详情和列表时实时汇总库存
4. 未上传药品图片时自动回填默认图片地址
5. 按批号效期库存顺序执行自动扣减
6. 库存进入预警区后触发低库存消息，恢复安全区后重置提醒周期


## 6. 初始化数据口径

当前初始化脚本已包含以下默认数据：

1. 8 条药品单位种子数据
   - `片`
   - `粒`
   - `支`
   - `袋`
   - `盒`
   - `瓶`
   - `ml`
   - `g`
2. 2 条系统药品示例数据
   - `阿司匹林肠溶片`
   - `二甲双胍片`

系统药品示例已直接写入：

1. `stock_unit_id = 1`
2. `stock_unit = '片'`


## 7. 当前不做的事情

为了控制本期改动范围，以下能力暂不在本次实现内：

1. 单位换算
2. 一药多图
3. 图片 OCR 识别
4. 数据库物理外键
5. 已有库存场景下的单位迁移与自动换算


## 8. 后续扩展建议

后续如果继续增强药品能力，建议按以下顺序推进：

1. 增加临期提醒
2. 增加批次级别库存调整与作废能力
3. 增加系统药品图片与单位图标后台维护
4. 评估是否把 `stock_unit` 文本快照进一步收敛为纯主数据引用
