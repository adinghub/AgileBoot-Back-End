# 检查报告与健康问题关联设计

## 1. 背景说明

当前检查报告模块已经具备上传、结构化指标、异常分析、趋势对比、异常建议等能力。

随着用户真实使用场景变复杂，系统后续会同时接收多种医疗资料：

1. 体检报告
2. 检验报告
3. 检查报告
4. 影像报告
5. 病理报告
6. 门诊病历
7. 处方与医嘱
8. 出院小结

这些资料之间的医学含义并不完全相同。检查报告更多是“证据”，疾病诊断通常来自医生综合判断。

因此本设计明确一个边界：报告不直接强关联疾病，而是优先关联“报告所见、异常指标、健康问题、风险线索”。疾病诊断只在来源足够明确时再建立关系。


## 2. 设计目标

本功能设计目标如下：

1. 建立报告到健康问题的标准关联模型
2. 避免把单个异常指标误判成疾病诊断
3. 支持用户看病时上传多份报告后形成证据链
4. 支持 App 端按健康问题聚合展示相关报告和异常变化
5. 为后续医生诊断、AI 总结、随访任务、健康档案页预留扩展空间


## 3. 核心原则

### 3.1 报告是证据，不是诊断

报告本身只记录某次检查或检验结果。

例如：

1. 空腹血糖偏高，不等于已经确诊糖尿病
2. 尿酸偏高，不等于已经确诊痛风
3. 肺部小结节，不等于肺癌
4. 白细胞升高，不等于某一种具体感染

所以报告详情页可以提示“异常”“风险”“建议复查”，但不应直接展示为“已患某疾病”。

### 3.2 健康问题是长期管理入口

健康问题用于承接多份报告里的共同线索。

例如：

1. 多次血糖偏高可以聚合到“糖代谢异常风险”
2. 多次尿酸偏高可以聚合到“尿酸偏高管理”
3. 甲状腺彩超异常可以聚合到“甲状腺结节随访”
4. 肝功能异常和脂肪肝可以聚合到“肝脏健康问题”

这样用户看到的是一个可持续跟踪的问题，而不是零散的一堆报告。

### 3.3 疾病诊断需要明确来源

疾病诊断只在以下来源明确时建立：

1. 门诊病历中的医生诊断
2. 出院小结中的出院诊断
3. 处方或医嘱中明确对应的诊断
4. 用户手动确认的既往病史
5. 后续医生端审核确认的诊断

AI 或规则引擎可以输出“可能相关风险”，但不能自动写成“已确诊疾病”。


## 4. 概念模型

### 4.1 Report 报告

Report 表示一次上传或录入的检查报告或其他医疗资料。

当前已有 `health_report` 可以继续作为检查报告主表基础。体检报告、检验报告、影像报告、病理报告等都可以通过 `report_type` 作为检查报告的细分类型承载。

核心含义：

1. 谁的报告
2. 什么时间的报告
3. 哪家机构的报告
4. 报告原始文件在哪里
5. 报告解析出了哪些结构化结果

### 4.2 Finding 报告所见

Finding 表示从报告中抽取出的医学事实。

当前 `health_report_item` 已经承担了结构化指标结果的一部分职责，后续可以继续增强为更通用的报告所见。

常见 Finding 包括：

1. 血糖偏高
2. 尿酸偏高
3. 总胆固醇偏高
4. 肝功能异常
5. 甲状腺结节
6. 肺部小结节
7. 脂肪肝
8. 白细胞升高

Finding 的定位是“事实记录”，不直接等价于疾病。

### 4.3 Health Problem 健康问题

Health Problem 表示需要长期关注、复查或管理的问题。

它可以来自：

1. 单份报告的明显异常
2. 多份报告的重复异常
3. 用户主动添加
4. 医生诊断转换
5. AI 或规则引擎生成后由用户确认

健康问题可以是疾病，也可以不是疾病。

例如：

1. 糖代谢异常风险
2. 尿酸偏高管理
3. 甲状腺结节随访
4. 肺结节随访
5. 肝功能异常
6. 高血压管理
7. 糖尿病管理

### 4.4 Diagnosis 疾病诊断

Diagnosis 表示明确的医学诊断。

它必须具备诊断来源，不能只根据单个指标自动产生。

诊断来源建议记录：

1. `source_type`：来源类型，如门诊病历、出院小结、用户确认、医生审核
2. `source_id`：来源业务ID
3. `diagnosis_name`：诊断名称
4. `diagnosis_date`：诊断日期
5. `confirm_status`：确认状态


## 5. 推荐关联关系

### 5.1 总体链路

推荐采用以下链路：

```text
报告 Report
  -> 报告所见 Finding
  -> 健康问题 Health Problem
  -> 疾病诊断 Diagnosis
```

其中：

1. Report 到 Finding 是强关联
2. Finding 到 Health Problem 是可解释关联
3. Health Problem 到 Diagnosis 是可选关联
4. Report 不直接强绑定 Diagnosis

### 5.2 示例一：血糖偏高

```text
检查报告
  -> 空腹血糖 6.4 mmol/L，偏高
  -> 糖代谢异常风险
  -> 可能相关：糖尿病前期 / 糖尿病
```

说明：

1. 报告里保存血糖结果
2. 系统可以建立“糖代谢异常风险”健康问题
3. 疾病只展示为可能相关风险，不直接写入确诊糖尿病

### 5.3 示例二：肺部小结节

```text
胸部 CT
  -> 右肺 4mm 小结节
  -> 肺结节随访
  -> 不直接关联肺癌诊断
```

说明：

1. 影像报告所见是“小结节”
2. 健康问题是“肺结节随访”
3. 只有医生明确诊断时，才建立疾病诊断

### 5.4 示例三：门诊确诊高血压

```text
门诊病历
  -> 医生诊断：高血压
  -> 高血压管理
  -> 高血压诊断
```

说明：

1. 门诊病历可以直接提供诊断证据
2. 系统可以同时建立健康问题和疾病诊断
3. 后续血压记录、用药计划、复诊任务都可以挂到该健康问题下


## 6. 一期功能范围

### 6.1 建议实现

一期建议先实现以下能力：

1. 保留现有报告和指标结果模型
2. 新增健康问题概念，用于承接报告异常项
3. 从报告异常项生成或关联健康问题
4. 在健康问题详情页展示相关报告、相关异常项、趋势摘要
5. 在报告详情页展示“关联健康问题”，而不是“关联疾病”
6. 对可能疾病只做风险提示文案，不写入确诊疾病

### 6.2 暂不实现

一期暂不实现：

1. 自动确诊疾病
2. 自动生成处方或治疗方案
3. 疾病知识图谱完整建设
4. 医生端诊断审核流转
5. AI 自动写入确诊病史


## 7. 数据模型建议

### 7.1 健康问题表 `health_problem`

建议新增健康问题主表。

核心字段：

1. `problem_id`
2. `owner_user_id`
3. `member_id`
4. `problem_name`
5. `problem_type`
6. `problem_status`
7. `risk_level`
8. `source_type`
9. `source_id`
10. `first_found_date`
11. `last_follow_date`
12. `summary`
13. `remark`

字段说明：

1. `problem_type` 用于区分风险、异常、随访、已诊断疾病等类型
2. `problem_status` 用于表示关注中、已稳定、已关闭等状态
3. `risk_level` 用于支持首页或健康档案排序
4. `source_type` 和 `source_id` 用于记录该问题最初由哪份报告或哪条诊断产生

### 7.2 健康问题证据表 `health_problem_evidence`

建议新增健康问题证据表，用于把报告、指标、诊断等资料挂到同一个问题下。

核心字段：

1. `evidence_id`
2. `problem_id`
3. `owner_user_id`
4. `member_id`
5. `evidence_type`
6. `evidence_id_ref`
7. `report_id`
8. `report_item_id`
9. `evidence_title`
10. `evidence_summary`
11. `evidence_date`
12. `confidence_level`
13. `confirm_status`
14. `remark`

字段说明：

1. `evidence_type` 可取报告、指标结果、影像所见、医生诊断、用户记录等
2. `evidence_id_ref` 指向对应业务数据ID
3. `report_id` 和 `report_item_id` 用于快速回到原始报告上下文
4. `confidence_level` 用于区分规则命中、AI 推断、人工确认等可信程度
5. `confirm_status` 用于记录是否已由用户或医生确认

### 7.3 疾病诊断表 `health_diagnosis`

疾病诊断建议独立建表，不和健康问题混在一起。

核心字段：

1. `diagnosis_id`
2. `owner_user_id`
3. `member_id`
4. `problem_id`
5. `diagnosis_name`
6. `diagnosis_code`
7. `diagnosis_date`
8. `source_type`
9. `source_id`
10. `confirm_status`
11. `remark`

字段说明：

1. `problem_id` 可以为空，因为某些历史诊断可能暂时没有归入健康问题
2. `diagnosis_code` 后续可接 ICD 或本地疾病字典
3. `confirm_status` 必须明确诊断是否已确认


## 8. 业务规则

### 8.1 报告详情页规则

报告详情页建议展示：

1. 报告基础信息
2. 原始报告文件
3. 结构化指标或报告所见
4. 异常摘要
5. 关联健康问题
6. 后续建议

报告详情页不建议直接展示“确诊疾病”，除非该报告本身就是门诊病历、出院小结等明确诊断来源。

### 8.2 健康问题详情页规则

健康问题详情页建议展示：

1. 问题名称
2. 当前状态
3. 风险等级
4. 相关报告
5. 相关异常项
6. 趋势变化
7. 复查或随访建议
8. 相关用药计划

健康问题详情页是后续健康档案的核心入口。

### 8.3 疾病诊断写入规则

系统只有在以下情况下写入疾病诊断：

1. 用户手动维护既往病史
2. 医生诊断文本被结构化解析并明确标注为诊断
3. 出院小结中存在明确诊断字段
4. 后台或医生端人工确认

仅凭报告指标异常不能写入疾病诊断。

### 8.4 AI 输出规则

AI 可以输出：

1. 异常解释
2. 可能相关风险
3. 建议复查方向
4. 建议就医科室
5. 需要关注的健康问题

AI 不应自动输出：

1. 已确诊疾病
2. 治疗处方
3. 药品用法用量
4. 替代医生判断的医学结论


## 9. 前端展示建议

### 9.1 报告详情页

建议文案使用：

1. “发现 3 项异常”
2. “已关联 2 个健康问题”
3. “可能需要关注：糖代谢异常风险”
4. “建议结合医生意见复查确认”

避免使用：

1. “你已患糖尿病”
2. “系统诊断为痛风”
3. “肺结节提示肺癌”

### 9.2 健康档案页

建议把用户的长期信息按健康问题聚合：

1. 糖代谢异常风险
2. 尿酸偏高管理
3. 血脂异常管理
4. 肝脏健康问题
5. 肺结节随访

每个健康问题下再展示：

1. 相关报告
2. 关键指标趋势
3. 建议动作
4. 最近更新时间


## 10. 后续演进

后续可以分阶段增强：

1. 建立常见指标到健康问题的规则映射
2. 建立健康问题到首页待跟进事项的联动
3. 建立健康问题到用药计划、复诊提醒的联动
4. 引入疾病字典和 ICD 编码
5. 引入医生端确认流程
6. 引入 AI 解释但保留人工确认边界


## 11. 结论

报告不要直接强关联疾病。

更合理的设计是：

```text
报告
  -> 报告所见 / 异常指标
  -> 健康问题 / 风险线索
  -> 疾病诊断
```

这样既能让用户把体检报告、看病检查报告、影像报告等资料串起来，又不会把系统变成自动诊断工具。

一期优先把“健康问题”和“证据链”做扎实，疾病诊断作为明确来源后的高级能力逐步补齐。
