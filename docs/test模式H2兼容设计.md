# test 模式 H2 兼容设计

## 1. 背景

项目已经把正式数据库基线切换为 PostgreSQL，但 `test` 模式仍然使用 H2 内存数据库做快速启动和单测支撑。

直接让 H2 执行 PostgreSQL 初始化脚本会出现兼容性问题，例如：

1. `serial8`
2. `TIMESTAMPTZ`
3. `setval(...)`
4. `ON CONFLICT ... DO NOTHING`

这些语法在 PostgreSQL 中是合法的，但 H2 即使开启 `MODE=PostgreSQL`，也不能完整无差别兼容。

## 2. 设计目标

本次兼容的目标是：

1. 保持 PostgreSQL 作为正式运行数据库基线不变
2. 保持 `test` 模式继续使用 H2 内存库，启动速度快、运行成本低
3. 让 H2 的表结构尽量贴近 PostgreSQL 正式表结构
4. 让后台基础能力和健康业务能力都能在 `test` 模式下完成初始化

## 3. 方案选择

本次没有回退 PostgreSQL 基线，也没有把 `test` 模式切成真实 PostgreSQL/Testcontainers，而是采用“独立维护一套 H2 兼容脚本”的方案。

原因如下：

1. 对当前工程侵入最小
2. 启动速度仍然快
3. 不依赖开发机本地 PostgreSQL
4. 便于继续承接现有单测和本地 smoke test

## 4. 落地内容

### 4.1 新增 H2 基础脚本

新增文件：

1. `healthtrail-infrastructure/src/main/resources/h2sql/healthtrail_test_schema.sql`
2. `healthtrail-infrastructure/src/main/resources/h2sql/healthtrail_test_data.sql`

处理原则：

1. 表结构字段与 PostgreSQL 基线保持一致
2. `serial8` 改为 `BIGINT GENERATED BY DEFAULT AS IDENTITY`
3. `TIMESTAMPTZ` 改为 `TIMESTAMP`
4. PostgreSQL 的 `setval` 改为 H2 的 `ALTER TABLE ... RESTART WITH ...`

### 4.2 新增健康业务 H2 脚本

新增文件：

1. `healthtrail-infrastructure/src/main/resources/h2sql/health_test_schema.sql`
2. `healthtrail-infrastructure/src/main/resources/h2sql/health_test_data.sql`

覆盖能力包括：

1. App 用户
2. 家庭成员
3. 药品
4. 用药计划与提醒
5. 体检报告与指标
6. 设备登记
7. 消息中心
8. 待跟进任务
9. 运营任务
10. 家庭共享/邀请
11. 指标模板

### 4.3 切换 test 配置

已修改：

1. `healthtrail-admin/src/main/resources/application-test.yml`
2. `healthtrail-domain/src/test/resources/application-test.yml`

调整点：

1. `spring.sql.init.platform` 改为 `h2`
2. `schema-locations` 改为加载 H2 专用基础脚本和健康脚本
3. `data-locations` 改为加载 H2 专用种子数据
4. 补充 `validationQuery: SELECT 1` 等 Druid 校验参数

### 4.4 新增回归测试

新增文件：

1. `healthtrail-admin/src/test/java/com/healthtrail/admin/config/TestProfileH2InitializationTest.java`

这条测试专门验证：

1. `basic,test` Profile 下 Spring 上下文可以正常启动
2. `sys_user`、`sys_menu` 等基础表已经完成初始化
3. `health_drug`、`health_medication_plan`、`health_report`、`health_indicator_template` 等健康表已经完成初始化
4. 基础种子数据和健康模块种子数据已经正确写入

这样后续只要有人改坏 H2 脚本、Profile 配置或初始化顺序，CI 就会直接失败，而不是等到手工启动时才发现。

## 5. 为什么不直接复用 pgsql 脚本

因为 `test` 模式的目标不是“验证 PostgreSQL 自身”，而是“在本地快速把应用和领域能力拉起来做开发验证”。

如果继续强行让 H2 直接执行 PostgreSQL 脚本，会带来两个问题：

1. 启动经常被数据库方言差异阻断
2. 每次 PostgreSQL 脚本加入新语法时，`test` 模式都会再次失效

因此把 H2 脚本明确拆分出来，更符合当前工程的开发体验需求。

## 6. 后续维护约束

为了避免两套脚本长期漂移，后续维护建议遵循以下约束：

1. PostgreSQL 脚本新增表或字段时，必须同步更新 H2 `*_test_schema.sql`
2. PostgreSQL 初始化有新的关键默认数据时，必须评估是否同步到 H2 `*_test_data.sql`
3. 仅在 H2 无法支持的 PostgreSQL 方言上做兼容性替换，不要擅自改业务字段语义
4. 每次数据库结构调整后，至少做一次 `basic,test` 启动验证
5. 每次数据库结构调整后，也要确保 `TestProfileH2InitializationTest` 继续通过
