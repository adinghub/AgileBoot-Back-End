# APP端用药计划结束日期清空修复设计

## 背景

App 端编辑用药计划时，用户可以点击“清空结束日期”，把原本有限期计划改回长期计划。  
但线上现象是：

1. 页面里结束日期已经被清空；
2. 点击保存后接口请求成功；
3. 再次查看计划详情时，旧结束日期仍然存在。

这会直接影响两类业务体验：

1. 用户误以为计划已经改为长期计划，实际后端仍按旧结束日期截断；
2. 提醒重建时仍使用历史结束日期，导致长期提醒提前停止。

## 根因分析

前端提交的数据本身没有问题，`endDate` 能正常以 `null` 传到后端。  
真正的问题出在 MyBatis-Plus 更新策略：

1. 用药计划更新最终走的是 `updateById()`；
2. `end_date` 字段未显式声明允许“更新为 null”；
3. 在默认更新策略下，实体属性为 `null` 时，该字段会被直接跳过；
4. 结果是数据库里原有的结束日期被保留，清空动作失效。

也就是说，这不是“前端没传值”，而是“后端收到了 null，但 ORM 把这次清空当成了无需更新”。

## 修复目标

1. 用户在 App 端清空结束日期后，数据库里的 `end_date` 必须同步更新为 `null`；
2. 该修复只影响“结束日期允许被清空”这一条链路，不扩大其它字段的 null 更新范围；
3. 补一条集成测试，覆盖“先有结束日期，再编辑清空”的真实场景。

## 方案设计

### 1. 仅对 `end_date` 字段放开 null 更新

在 `HealthMedicationPlanEntity.endDate` 上显式声明：

- `@TableField(updateStrategy = FieldStrategy.IGNORED)`

这样做的意图是：

1. 仅允许 `end_date` 在更新时写入 `null`；
2. 不改动全局 MyBatis-Plus 更新策略；
3. 避免其它字段因为全局放开 null 更新而产生不可预期覆盖。

### 2. 增加集成测试

在 API 集成测试里补一条完整回归：

1. 新增一条带结束日期的用药计划；
2. 调用更新逻辑，把 `endDate` 设为 `null`；
3. 重新查库断言 `end_date` 已被真正清空。

这条测试的价值在于，它验证的是最终持久化结果，而不是只验证命令对象或模型内存态。

## 影响范围

本次改动只涉及：

1. 用药计划实体映射 `HealthMedicationPlanEntity`
2. API 集成测试 `DrugInventoryFlowTest`

不会改变：

1. 前端表单交互
2. 用药计划新增逻辑
3. 其它字段的更新策略

## 验证重点

修复后需重点验证：

1. 编辑已有计划并清空结束日期，保存后再次打开仍为空；
2. 原本有结束日期的计划改为长期计划后，提醒不会再因旧结束日期停止；
3. 仍保留填写结束日期的正常编辑能力，不影响普通修改流程。
