# 推送消息业务载荷设计

## 1. 功能目标

当前系统已经具备：

1. App 设备注册
2. 用药提醒 Push 派发
3. 首页任务跳转参数
4. 任务详情推荐动作

但通知链路和任务链路仍然是两套表达方式。

这会导致：

1. App 点击通知后还要单独维护一套路由判断
2. 通知入口和首页任务入口可能落到不同页面区域
3. 后续接入站内信、消息中心时会继续重复定义业务载荷

因此本期补充统一的推送业务透传载荷。


## 2. 设计原则

### 2.1 推送文案与推送业务载荷分离

Push 通道通常至少有两类数据：

1. 给用户看的标题/正文
2. 给客户端透传消费的业务载荷

当前新增 `HealthAppPushPayloadDTO`，专门承接第二类数据。

### 2.2 复用任务体系结构

本次提醒 Push 透传载荷直接复用：

1. `navigation`
2. `recommendedAction`

这样用户从通知进入和从首页任务进入时：

1. 跳转页面一致
2. 页面内落点一致
3. 推荐动作一致


## 3. 当前落地范围

### 3.1 用药提醒通知

本期先把统一透传载荷接入到：

`MedicationReminderNotice`

透传字段包括：

1. `businessScene`
2. `businessId`
3. `title`
4. `content`
5. `navigation`
6. `recommendedAction`

### 3.2 报告建议通知

本期继续把统一透传载荷接入到：

`HealthReportAdviceNotice`

透传字段与提醒通知保持一致：

1. `businessScene`
2. `businessId`
3. `title`
4. `content`
5. `navigation`
6. `recommendedAction`

### 3.3 当前同时复用到消息中心

本次统一业务载荷不仅用于设备 Push，
也同步用于 App 消息中心落库。

这样客户端从：

1. Push 点击
2. 消息中心点击

进入业务页时，都可以共用同一份 `navigation` 和 `recommendedAction`。


## 4. 规则设计

### 4.1 提醒通知导航规则

提醒通知统一返回：

1. `targetPageCode = MEDICATION_REMINDER_DETAIL`
2. `targetTabCode = PROCESS`
3. `targetAnchorCode = REMINDER_FEEDBACK`

### 4.2 提醒通知推荐动作规则

提醒通知只会在“已到提醒时间”的场景派发，
因此推荐动作默认按高优先关注处理：

1. `actionPriority = 1`
2. `riskLevel = HIGH`
3. `actionText = 去处理提醒`


## 5. 后续建议

建议下一步继续补：

1. 增加消息中心落库表
2. App 端统一把通知点击与首页任务点击收敛到一套路由解析器
3. 继续扩展新的业务场景载荷
