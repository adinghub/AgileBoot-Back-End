# 用药提醒定时任务设计

## 1. 设计目标

当前用药计划在新增、修改时已经会立即生成提醒记录，但一期仅靠这个入口还不够稳。

补本次定时任务的目标是：

1. 自动把过点未处理提醒改成已过期
2. 自动补齐未来窗口期内缺失的提醒记录
3. 为后续 App Push、站内消息、短信提醒预留稳定数据层


## 2. 为什么要补定时任务

如果只在用户查询“今日提醒”时才顺手过期提醒，会有几个问题：

1. 用户长时间不打开提醒页时，数据库里会长期保留错误的待处理状态
2. 后续统计“漏服、已过期、依从性”时，数据不够实时
3. 如果后续有推送通道，需要依赖稳定的提醒状态和未来提醒数据

因此需要把提醒状态维护从“用户访问时顺带处理”升级成“系统后台持续维护”。


## 3. 本次落地范围

### 3.1 自动过期任务

默认每 5 分钟执行一次：

1. 查询所有 `待处理` 且 `scheduled_time < 当前时间` 的提醒
2. 批量改成 `已过期`

### 3.2 自动补齐任务

默认每 6 小时执行一次：

1. 查询状态为正常且日期仍有效的用药计划
2. 以“今天开始未来 7 天”为窗口
3. 对每个计划检查窗口内缺失的提醒记录
4. 只补缺失记录，不重建已有记录


## 4. 关键设计点

### 4.1 定时任务只放在 API 端

项目里同时有：

1. `healthtrail-api`
2. `healthtrail-admin`

并且两个启动端都启用了 Spring Scheduling。

如果把用药提醒定时任务放在公共模块里，两个服务进程会同时执行，容易造成重复补齐。

因此本次定时任务类放在 `healthtrail-api` 模块，保证默认只由 App 服务运行。

### 4.2 采用“补齐”而不是“重建”

定时任务不会删除原有提醒记录，只会补齐缺失提醒。

这样做的好处是：

1. 不会误伤用户已经产生状态流转的提醒
2. 对历史数据更安全
3. 后续便于平滑扩展推送发送状态

### 4.3 不做数据库唯一索引防重

当前提醒表使用逻辑删除字段 `deleted`。

如果直接对 `(plan_id, scheduled_time)` 做唯一索引，会和逻辑删除后的历史提醒冲突，不利于后续计划重建。

因此本次采用：

1. 代码层按 `plan_id + scheduled_time` 查重
2. 数据库层补组合普通索引，加快查重查询


## 5. 当前默认配置

默认配置通过注解里的占位符提供：

1. 过期任务 cron：每 5 分钟一次
2. 补齐任务 cron：每 6 小时一次
3. 派发任务 cron：每分钟一次
4. 补齐窗口：未来 7 天

后续如果要调整频率，可在 `api` 侧配置中覆盖：

1. `health.medication.reminder.schedule.expire-cron`
2. `health.medication.reminder.schedule.generate-cron`
3. `health.medication.reminder.schedule.dispatch-cron`
4. `health.medication.reminder.schedule.generate-window-days`


## 6. 后续建议

建议下一步继续补：

1. 真实 App Push 或站内信发送器接入
2. App Push/短信/站内信通道接入
3. 分布式锁，避免多实例部署时重复执行定时任务
4. 手动补齐接口，方便运营或开发排查
