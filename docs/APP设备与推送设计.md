# APP设备与推送设计

## 1. 设计目标

为了让用药提醒真正具备“发到用户手机设备”的能力，本次补充 App 设备与 Push 基础能力。

目标如下：

1. App 登录后可上报当前设备 Token
2. 后端可记录一个用户绑定的多个设备
3. 用药提醒派发时按设备维度发送
4. 后续可平滑接入真实 Push 厂商 SDK


## 2. 核心设计

### 2.1 新增设备表

新增 `health_app_device` 表，用于保存：

1. 当前归属用户
2. 设备唯一编码
3. 推送平台
4. 设备 Token
5. 设备型号、厂商、系统版本、App版本
6. 最后活跃时间

### 2.2 一人多设备

当前设计支持：

1. 一个用户绑定多个设备
2. 同一设备切换账号时重新绑定到新账号

因此设备表不直接挂在登录 Token 上，而是独立维护。

### 2.3 设备编码唯一

`device_code` 全局唯一。

这样做的好处：

1. App 重装前后可区分不同安装实例
2. 同一设备切换账号时可直接覆盖归属关系
3. 避免同一设备反复注册出多条脏数据

### 2.4 Push 发送器升级

在上一轮的提醒发送通道基础上，本次发送器从“纯日志模拟”升级为“基于设备 Token 的派发”：

1. 先查当前用户的活跃设备
2. 再逐设备派发提醒
3. 当前仍使用日志模拟厂商发送
4. 但发送入口已经按真实设备维度组织


## 3. 接口设计

### 3.1 注册设备

`POST /app/push/devices`

用途：

1. App 首次启动后注册设备
2. Push Token 刷新后重新上报
3. 用户切换账号后重新绑定设备

### 3.2 查询当前用户设备列表

`GET /app/push/devices`

用途：

1. 方便前端查看当前账号下活跃设备
2. 便于后续做设备管理页

### 3.3 停用设备

`DELETE /app/push/devices/{deviceCode}`

用途：

1. 用户退出设备登录
2. 用户关闭消息提醒
3. 设备失效时停用


## 4. 当前阶段说明

当前 Push 发送链路已经做到：

1. 有设备数据源
2. 有按设备派发逻辑
3. 有提醒发送状态回写

但还没有做到：

1. 对接厂商 SDK
2. 真正投递系统通知栏
3. 设备离线回执处理
