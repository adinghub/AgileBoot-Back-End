# 后台首页运营任务管理设计

## 1. 功能目标

本功能用于给后台管理端提供“首页运营任务”的维护入口，覆盖以下场景：

1. 按 App 用户、家庭成员、风险等级、状态检索运营任务
2. 为指定 App 用户新增一条首页待跟进运营任务
3. 为任务配置统一业务跳转参数，驱动 App 打开消息中心、用药计划、今日提醒或报告详情
4. 维护任务生效时间窗口，控制任务何时出现在首页
5. 对已配置任务进行修改和删除，支持运营快速纠偏

## 3. 设计原则

### 3.1 运营任务复用首页任务流协议，而不是单独再造一套跳转模型

后台运营任务虽然是人工投放的任务，但它最终仍然落在 App 首页“待跟进任务流”里，因此直接复用现有统一导航协议：

1. `targetPageCode`
2. `targetBizId`
3. `targetBizType`
4. `targetTabCode`
5. `targetAnchorCode`

这样可以保证：

1. App 首页、消息中心、待跟进事项使用同一套跳转语义
2. 后端无需为运营任务单独维护另一套客户端路由规则
3. 后续新增业务落点时，运营任务可以自然复用

### 3.2 后台只做“任务投放配置”，不代替底层业务主数据

后台运营任务页面允许配置页面编码和业务主键，但不负责创建底层药品、提醒、报告等原始业务数据。

这样做的原因是：

1. 运营任务的职责是“引导用户去某个业务页处理事情”
2. 底层提醒、报告、消息仍然应由各自业务模块维护
3. 避免后台在运营页里过度耦合其它业务的创建流程

### 3.3 生效窗口优先级高于展示配置

首页只消费“当前时刻处于启用状态且命中时间窗口”的运营任务，因此后台页面和服务层都把时间窗口作为关键配置。

具体约束：

1. `startTime` 默认为当前分钟
2. `endTime` 可留空，表示长期有效
3. 若同时填写开始和结束时间，则开始时间不能晚于结束时间

## 4. 接口设计

### 4.1 分页列表

- 接口：`GET /health/operation-tasks`
- 权限：`health:operationTask:list`

查询参数：

1. `pageNum`
2. `pageSize`
3. `ownerUserId`
4. `memberId`
5. `riskLevel`
6. `status`
7. `keyword`

列表核心字段：

1. `operationTaskId`
2. `ownerUserId`
3. `memberId`
4. `taskTitle`
5. `taskContent`
6. `actionText`
7. `riskLevel`
8. `riskLevelName`
9. `priorityWeight`
10. `targetPageCode`
11. `targetPageName`
12. `targetBizId`
13. `targetBizType`
14. `targetTabCode`
15. `targetAnchorCode`
16. `targetAnchorName`
17. `startTime`
18. `endTime`
19. `status`
20. `remark`
21. `createTime`

### 4.2 详情接口

- 接口：`GET /health/operation-tasks/{operationTaskId}`
- 权限：`health:operationTask:query`

说明：

1. 编辑前前端始终拉详情，不直接使用列表行数据回填
2. 这样即使后续列表列做裁剪，编辑弹窗仍然能拿到完整字段

### 4.3 新增接口

- 接口：`POST /health/operation-tasks`
- 权限：`health:operationTask:add`

请求体重点字段：

1. `ownerUserId`
2. `memberId`
3. `taskTitle`
4. `taskContent`
5. `actionText`
6. `riskLevel`
7. `priorityWeight`
8. `targetPageCode`
9. `targetBizId`
10. `targetBizType`
11. `targetTabCode`
12. `targetAnchorCode`
13. `startTime`
14. `endTime`
15. `status`
16. `remark`

### 4.4 修改接口

- 接口：`PUT /health/operation-tasks/{operationTaskId}`
- 权限：`health:operationTask:edit`

说明：

1. 修改接口与新增接口共用同一套字段结构
2. 后端会自动把路径参数写回 `operationTaskId`

### 4.5 删除接口

- 接口：`DELETE /health/operation-tasks/{operationTaskId}`
- 权限：`health:operationTask:remove`

## 5. 页面设计

### 5.1 搜索区

后台搜索区提供以下筛选项：

1. App 用户 ID
2. 成员 ID
3. 风险等级
4. 状态
5. 关键字

### 5.2 列表区

列表页重点突出后台最关心的信息：

1. 任务投放给谁
2. 风险等级和优先级
3. 最终会跳到哪个 App 页面
4. 当前是否在生效窗口内

### 5.3 编辑弹窗

编辑弹窗按“投放对象 + 任务内容 + 跳转参数 + 生效时间 + 备注”拆分字段，目的是：

1. 让运营配置过程接近真实业务思路
2. 降低页面编码、锚点编码等协议字段的理解门槛
3. 方便前后端联调时快速核对同一条任务

## 6. 权限设计

后台权限与控制器一一对应：

1. 列表：`health:operationTask:list`
2. 详情：`health:operationTask:query`
3. 新增：`health:operationTask:add`
4. 修改：`health:operationTask:edit`
5. 删除：`health:operationTask:remove`

说明：

1. 前端页面按钮通过 `v-auth` 控制显隐
2. 后端接口仍然以 `@PreAuthorize` 作为最终权限兜底

## 7. 风险与边界

当前后台能力仍保持这些边界：

1. 不在运营任务页直接创建提醒、报告等底层业务数据
2. 不在运营任务页直接预览 App 真实页面，只维护跳转协议
3. 不做批量导入和批量复制任务，本期先保证单条 CRUD 稳定

原因是：

1. 本期目标是补齐首页运营任务投放能力，而不是扩展成完整运营编排平台
2. 页面编码和锚点已经足够支撑当前 App 首页引导链路

## 8. 验收建议

建议按以下步骤验收：

1. 新增一条启用中的运营任务，确认列表刷新后能看到任务
2. 配置 `targetPageCode` 和 `targetAnchorCode`，确认后端自动回填展示名称
3. 修改任务风险等级、优先级和结束时间，确认保存成功
4. 将任务状态改为停用，确认首页聚合结果不再消费该任务
5. 删除任务，确认后台列表移除且 App 首页不再出现该运营任务
