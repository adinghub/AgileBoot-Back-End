# APP端消息中心设计

## 1. 功能目标

当前系统已经具备：

1. 用药提醒 Push 派发
2. 报告建议 Push 派发
3. 统一业务透传载荷
4. 首页任务跳转与推荐动作

但用户仍然存在两个实际问题：

1. 如果设备没有注册 Token，Push 发不出去，用户就看不到这条通知
2. 如果用户错过了系统通知，App 内没有统一消息入口做回看

因此本期补充 App 消息中心，形成：

1. 业务消息统一落库
2. Push 派发结果可追踪
3. App 端统一消息列表、详情、已读能力
4. 报告建议基础去重


## 2. 设计原则

### 2.1 消息中心与 Push 通道解耦

消息中心表负责保存“业务消息快照”，
Push 只是消息的一种送达通道。

这样即使 Push 失败，消息仍然存在于 App 消息中心。

### 2.2 统一复用现有业务透传载荷

消息中心详情不重新设计一套跳转协议，
继续复用：

1. `HealthAppPushPayloadDTO`
2. `navigation`
3. `recommendedAction`

这样 App 从：

1. 系统 Push
2. 消息中心
3. 首页待跟进任务

进入业务页时，都能共用同一套路由解析逻辑。

### 2.3 去重按业务语义设计

不同业务的去重粒度不同：

1. 用药提醒按“提醒ID”去重
2. 报告建议按“报告ID + 当前异常项签名”去重

这样既能避免重复消息，
又不会阻止真正新的业务变化进入消息中心。


## 3. 数据模型

### 3.1 新增表

新增：

`health_app_message`

核心字段包括：

1. `owner_user_id`：归属 App 用户
2. `member_id`：家庭成员 ID
3. `member_name_snapshot`：成员名称快照
4. `business_scene`：业务场景
5. `business_id`：业务主键
6. `message_title`：消息标题
7. `message_content`：消息正文
8. `payload_json`：统一业务透传载荷
9. `dedup_key`：去重键
10. `read_status`：已读状态
11. `read_time`：已读时间
12. `send_status`：最近一次发送状态
13. `send_time`：最近一次发送时间
14. `send_channel`：最近一次发送通道
15. `send_retry_count`：发送重试次数
16. `send_result_message`：最近一次发送结果说明

### 3.2 状态说明

#### 已读状态

1. `0`：未读
2. `1`：已读

#### 发送状态

1. `0`：待发送
2. `1`：发送成功
3. `2`：发送失败


## 4. 业务接入规则

### 4.1 用药提醒

流程如下：

1. 定时任务扫描到点提醒
2. 先创建或复用消息中心记录
3. 再走原有 Push 发送器
4. 发送结果回写到消息表和提醒表

这样同一条提醒多次重试发送时：

1. 不会重复创建消息
2. 会持续更新最近一次发送状态

### 4.2 报告建议

流程如下：

1. 保存报告结构化结果
2. 如果存在异常项，则构建建议消息
3. 先根据异常项签名判断是否已存在相同消息
4. 若不存在则创建消息并派发 Push
5. 发送结果回写消息表

### 4.3 报告建议去重规则

报告建议不按指标表主键去重，
因为保存指标采用的是“先删后存”，主键会变化。

因此当前使用：

1. `报告ID`
2. `异常项名称`
3. `异常标记`
4. `结果值`
5. `结果单位`

归一化后生成摘要签名，
再计算哈希作为去重键。


## 5. App 接口范围

本期开放以下接口：

1. `GET /app/messages`：消息列表
2. `GET /app/messages/{messageId}`：消息详情
3. `GET /app/messages/unread-count`：未读数量
4. `POST /app/messages/{messageId}/read`：单条已读
5. `POST /app/messages/read-all`：全部已读
