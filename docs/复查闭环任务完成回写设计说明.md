# 复查闭环任务完成回写设计说明

## 1. 背景

当前首页待跟进任务流已经统一承载三类任务：

1. 用药提醒待处理
2. 报告建议待跟进
3. 慢病复查、健康问题复查等运营任务

其中慢病复查和健康问题复查本质上不是普通运营投放，而是用户主动安排的一轮健康管理动作。原有任务流只会把 `follow_up_task` 标记为已完成，并不会同步更新慢病专项或健康问题的最近跟进时间，导致用户完成复查后，业务档案仍然看起来没有变化。

## 2. 目标

本次调整只补齐“完成复查任务后的业务回写”，不改变提醒、报告建议、普通运营任务的原有判断规则。

目标如下：

1. 慢病复查任务完成后，回写慢病专项 `lastReviewDate`。
2. 健康问题复查任务完成后，回写健康问题 `lastFollowDate`。
3. 健康问题复查完成时，追加一条状态时间线，便于用户在问题详情里看到处理记录。
4. 完成后停用对应 `operation_task`，避免同一轮复查继续在首页或慢病看板里反复出现。
5. 忽略、延后、恢复仍然只作用于首页任务流，不写业务主表。

## 3. 任务类型边界

### 3.1 提醒任务

提醒任务仍然不能在首页任务流里直接完成。

原因是提醒任务的真实闭环包含服药、跳过、库存恢复、历史记录等专属语义，必须回到提醒模块自己的动作完成。

### 3.2 报告建议任务

报告建议任务完成后只标记首页待跟进状态。

报告建议本身更像“已查看并处理本轮建议”，没有一个独立主表字段可以准确表达所有线下动作，因此本次不额外写报告主表。

### 3.3 复查类运营任务

只有以下 `targetBizType` 会触发业务回写：

1. `CHRONIC_REVIEW`
2. `HEALTH_PROBLEM_REVIEW`

普通运营任务仍然只作为首页引导，不会因为完成动作自动写入业务档案。

## 4. 后端处理流程

`HealthFollowUpTaskApplicationService#completeTask(...)` 仍然是统一完成入口。

处理顺序如下：

1. 校验任务类型和来源归属。
2. 写入或更新 `follow_up_task`，状态改为已完成。
3. 追加 `follow_up_task_log`。
4. 如果来源是复查类 `operation_task`，再执行业务回写。
5. 停用对应 `operation_task`。

这样可以保证首页任务状态和业务档案状态在同一个事务内完成，避免出现首页已完成但业务档案未更新的中间状态。

## 5. 慢病复查回写

当 `operation_task.targetBizType = CHRONIC_REVIEW` 时：

1. 使用 `targetBizId` 找到慢病专项档案。
2. 校验档案归属用户和成员与任务一致。
3. 更新 `lastReviewDate = completeTime`。
4. 如果用户填写了处理备注，同步写入专项备注字段。
5. 不自动修改专项状态。

不自动修改专项状态的原因是，“已复查”不等于“病情稳定”或“专项关闭”。状态变化仍应由用户在慢病专项页明确选择。

## 6. 健康问题复查回写

当 `operation_task.targetBizType = HEALTH_PROBLEM_REVIEW` 时：

1. 使用 `targetBizId` 找到健康问题。
2. 校验健康问题归属用户和成员与任务一致。
3. 更新 `lastFollowDate = completeTime`。
4. 如果用户填写了处理备注，同步写入健康问题备注字段。
5. 追加 `health_problem_status_log`，动作类型为 `REVIEW_TASK_COMPLETE`。
6. 不自动修改健康问题状态。

状态时间线的 `beforeStatus` 和 `afterStatus` 保持一致，表示这是一条“复查完成记录”，不是状态变更记录。

## 7. App 侧调整

首页待跟进项新增消费 `operationTaskId`。

App 侧统一用 `sourceId` 发起任务动作：

1. 提醒任务取 `reminderId`。
2. 报告建议任务取 `reportId`。
3. 运营任务取 `operationTaskId`。

“本轮已处理”按钮只展示给：

1. 报告建议任务。
2. `targetBizType` 为 `CHRONIC_REVIEW` 或 `HEALTH_PROBLEM_REVIEW` 的运营任务。

普通运营任务仍然只展示跳转和忽略/延后等任务流动作。

## 8. 兼容性

本次新增字段 `operationTaskId` 对旧版本 App 是向后兼容的：旧版本不消费该字段，不会影响已有提醒和报告建议任务。

后端完成动作也保持兼容：报告建议任务仍然只完成首页待跟进状态；提醒任务仍然拒绝直接完成。

## 9. 后续可扩展点

后续如果新增新的复查型运营任务，可以按同样方式扩展：

1. 约定新的 `targetBizType`。
2. 在完成动作里增加对应业务回写方法。
3. App 侧把该 `targetBizType` 纳入可完成运营任务白名单。

这样能继续复用首页任务流，同时避免把所有运营任务都错误当成业务闭环任务。
