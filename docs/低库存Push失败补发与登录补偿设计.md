# 低库存 Push 失败补发与登录补偿设计

## 1. 背景

当前低库存提醒已经具备以下能力：

1. 药品库存变动后自动判断是否进入预警区间。
2. 进入预警区间时生成 App 消息中心记录。
3. 同时尝试向当前用户的活跃设备发送 Push。

但联调中发现一个关键缺口：

1. 只要低库存消息记录创建成功，就会把 `low_stock_notified` 标记成 `true`。
2. 一旦当时没有活跃设备 Token，或者 Push 发送失败，这一轮低库存周期也会被提前结束。
3. 后续即使用户重新登录、重新上报 Token，也不会再收到这条低库存 Push。

这与业务预期不一致。预期应为：

1. 用户后来重新登录并上报 Token 后，仍然应该再收到一次低库存 Push。
2. 但一旦低库存 Push 已经真正发送成功，本轮提醒周期就可以结束，直到库存恢复安全后才重新开启下一轮。

## 2. 目标

本次调整聚焦两个目标：

1. 把“低库存周期是否结束”的判断，从“消息是否创建成功”改为“Push 是否发送成功”。
2. 在设备重新注册或刷新 Token 后，自动补发当前仍未送达成功的低库存提醒。

## 3. 设计方案

### 3.1 低库存周期完成条件改为 Push 成功

调整前：

1. 低库存消息创建成功后，就会把 `low_stock_notified = true`。
2. 即使 Push 失败，也不再继续补发。

调整后：

1. 低库存消息仍然照常落消息中心，保证站内消息可见。
2. 只有 `HealthAppMessageNotifyResult.success = true` 时，才回写：
   `low_stock_notified = true`
   `low_stock_notify_time = 发送成功时间`
3. 如果 Push 失败，只更新消息发送失败状态，不结束当前低库存周期。

### 3.2 同一轮低库存失败重试时复用原消息

低库存提醒不能简单增加固定 `dedupKey`，原因是：

1. 用户补库存恢复安全后，未来再次进入低库存时，应该产生一条新的消息记录。
2. 如果用固定 `dedupKey` 全局去重，会把不同低库存周期错误合并。

因此本次采用“最近一条消息复用”策略：

1. 按 `owner_user_id + business_scene=LOW_STOCK_ALERT + business_id=drug_id` 查询最近一条消息。
2. 如果最近一条消息发送状态不是成功，则复用该消息继续补发，并刷新消息快照内容。
3. 如果最近一条消息已经成功，则说明上一轮提醒已送达；当业务重新触发新一轮低库存时，允许重新创建新消息。

### 3.3 兼容修复历史脏数据

历史实现可能已经留下这类数据：

1. `low_stock_notified = true`
2. 但最近一条低库存消息的 `send_status != SUCCESS`

这代表“业务状态已经封口，但实际 Push 从未成功”。  
本次在低库存判断时增加自动修复：

1. 如果发现 `low_stock_notified = true`，但最近一条低库存消息并未成功发送，
2. 则自动把 `low_stock_notified` 和 `low_stock_notify_time` 回滚，
3. 让当前药品重新恢复为可补发状态。

### 3.4 设备重新注册后的补偿触发

设备注册接口 `POST /app/push/devices` 在以下场景都会被调用：

1. App 首次安装登录
2. Push Token 刷新
3. 用户切换账号重新登录

因此在设备注册成功后，追加一段“安静补偿逻辑”：

1. 扫描当前用户启用了库存跟踪且配置了预警阈值的个人药品。
2. 对当前仍低于预警值的药品重新执行低库存判断。
3. 若该药品当前周期尚未 Push 成功，则复用原消息或创建新消息补发。
4. 单条药品补发失败仅记日志，不影响设备注册接口成功返回。

## 4. 结果

调整完成后，低库存提醒行为会变成：

1. 低库存发生时，先落站内消息，再尝试设备 Push。
2. Push 失败不会结束本轮低库存周期。
3. 用户之后重新登录、重新上报 Token 时，会自动补发尚未成功送达的低库存提醒。
4. 一旦某轮低库存 Push 已经成功，本轮提醒结束，直到库存恢复安全再重新进入低库存时，才会开启下一轮提醒。
